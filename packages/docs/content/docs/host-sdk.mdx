---
title: Host and client contract
description: "The current Electron boundary, the missing shared host layer, and the June-first contract it must expose"
---

June's blueprint puts one host between the core and every UI. The host owns the durable session, agent loop,
provider connection, tools, and policy. Desktop, web, CLI, and IDE surfaces are peer clients of one versioned
contract.

That shared layer does not exist yet. `@june/protocol`, `@june/server`, and `@june/client` are reserved package
names with no directories. The Electron demo has a useful product-specific host boundary, but it must not be
mistaken for the future SDK.

## The boundary that exists

The desktop runtime is split in the correct direction:

```text
renderer
  -> window.june (preload facade)
  -> Electron IPC
  -> JuneHost (main process)
  -> AgentHarness + SqliteSessionRepo + provider stream
```

`contextIsolation`, sandboxing, disabled Node integration, and guarded external navigation keep runtime Core
objects out of the renderer. The preload exposes these eight operations:

| Operation     | Current behavior                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| `initialize`  | Load agent profiles, select the most recently updated conversation, and open a harness when authenticated |
| `login`       | Run the product's ChatGPT browser flow and reopen the active harness                                      |
| `send`        | Create a session when needed, name it from the prompt, run `harness.prompt`, and return a fresh snapshot  |
| `abort`       | Request abort only when the product's live harness state says it is streaming                             |
| `newChat`     | Close the active harness and session, then create a session for the chosen agent                          |
| `selectAgent` | Close the active session and open that agent's most recent conversation                                   |
| `updateAgent` | Persist name, role, and instructions; recreate the active harness when necessary                          |
| `onEvent`     | Subscribe to demo-local delta, running, status, error, and snapshot events                                |

`JuneHostDependencies` is a real improvement over product code that constructs authentication and streaming
inline. It injects `authStatus`, `login`, `createStreamFn`, model, and thinking level. The production composition
still intentionally chooses one provider (`openai-codex`) and `FileCredentialStore`; that is a demo choice, not
a Core default.

The host also closes its harness, active session, session repository, and profile repository. The Electron
`before-quit` handler starts that asynchronous close without waiting for it, so process-level shutdown remains
weaker than the host object's own teardown.

## What the demo proves and what it does not

| Proven                                                     | Not proven                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Core can live outside a sandboxed renderer                 | A stable or language-neutral wire                                              |
| One product can own profiles and per-agent conversations   | A general session list/open/switch contract                                    |
| A snapshot can be rebuilt from durable message entries     | An atomic snapshot plus live-event handoff                                     |
| Text deltas and running state can cross IPC                | Lossless transport of every Core event and content part                        |
| Provider composition can be injected into the product host | Provider discovery, selection, typed auth failure, or remote credential policy |
| Local teardown can be centralized                          | Guaranteed settlement of active commands and runs at process exit              |

The current snapshot contains agents, previews, authentication state, selected agent, message entries, and a
running boolean. It contains no session id, lane id, run id, event cursor, operation outcome, queued input,
running tool state, or suspended-operation status. `openHarness()` ignores the `suspended` value returned by
`AgentHarness.create()`. A restarted desktop client can therefore display history, but it cannot faithfully
offer resume or explain an interrupted operation.

`forward()` translates only `agent_start`, text `message_update`, and `agent_end`. Reasoning deltas, complete
message boundaries, tool lifecycle, usage, and turn errors are not forwarded. This is acceptable for the demo's
current UI; it is not an acceptable shared event contract.

## Protocol requirements

The first protocol is constrained by June's own core and blueprint, not by the shape of a single demo. It must:

1. Carry canonical messages and parts without provider-specific encoding or text flattening.
2. Give sessions, lanes, runs, tool calls, queue items, agents, and clients stable identities.
3. Represent admission separately from settlement: an accepted prompt may finish later or after reconnect.
4. Pair a snapshot with an event cursor so a client cannot miss changes between loading state and subscribing.
5. Preserve typed outcomes and errors instead of throwing unstructured strings across a transport.
6. Support local IPC, HTTP plus event streaming, and a non-TypeScript client from the same schema.
7. Keep policy decisions, credentials, tools, and durable state in the host; keep rendering in clients.
8. Include runtime decoding at every transport boundary.

The protocol should expose June concepts directly. It does not need to copy another project's endpoints,
conversation URLs, or core-internal lane API names.

## Minimum host surfaces

These are capability groups, not final method signatures. Exact names should be frozen only after the M0
correctness work in the [roadmap](./roadmap.mdx) settles the underlying lifecycle.

| Surface        | Required capability                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| Provider       | List providers and models, report typed auth state, drive serializable login interactions, select model and effort |
| Session        | Create, list, open, name, prompt, steer, follow up, queue for next run, abort, resume, close                       |
| Observation    | Load a reconnect-safe snapshot, watch from its cursor, query terminal outcomes and usage                           |
| History        | Read canonical entries, navigate branches, fork, checkpoint, revert, search projected text                         |
| Tool host      | List capabilities, bind an execution environment, stream updates, surface policy and approval state                |
| Agent          | List and configure agents, guidance, skills, and available capabilities with provenance                            |
| Administration | Health, schema/version negotiation, identity, access checks, and graceful shutdown                                 |

## Error and event discipline

The current demo mixes three failure styles: thrown `Error`, harness `Result.err`, and a successful run result
whose outcome is `failed`. The shared contract must preserve those distinctions in serializable form:

| Category             | Example                                                     | Transport behavior                                                  |
| -------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| Request rejection    | invalid input, closed session, lane busy                    | Typed response error; no run accepted                               |
| Accepted run outcome | completed, aborted, provider failure, harness failure       | Durable outcome addressed by run id                                 |
| Authentication state | not configured, expired, refresh failure, transport failure | Typed provider status; do not collapse every exception to "expired" |
| Storage failure      | lease lost, unsupported version, corruption                 | Typed host error with retryability and safe diagnostic fields       |
| Policy pause         | approval required                                           | Durable suspended state plus an approve/deny command                |

Events need stable ids or cursors and must describe state changes, not merely UI instructions. A client may
render a tool event as a card, a log line, or nothing at all. The host still carries it.

## Ownership

| Concern                                  | Core                                 | Host/server                        | Client                                                |
| ---------------------------------------- | ------------------------------------ | ---------------------------------- | ----------------------------------------------------- |
| Loop and durable operation state         | Owns                                 | Runs and coordinates               | Never owns                                            |
| Canonical entries, parts, events, errors | Defines with schema/protocol         | Validates and transports           | Consumes                                              |
| Provider credentials                     | Defines provider-facing abstractions | Selects storage and access policy  | Requests auth interaction; never receives raw secrets |
| Filesystem, shell, remote sandbox        | Defines tool contracts               | Binds the execution environment    | Shows intent, progress, output, and approval          |
| Skills and plugins                       | Defines lifecycle primitives         | Loads policy-approved capabilities | Browses and activates through the contract            |
| Presentation                             | No product chrome                    | No product chrome                  | Owns layout and interaction                           |

## Implementation order

1. Fix the harness admission, settlement, abort, observer, identity, and validation gaps in roadmap M0.
2. Define canonical parts, errors, snapshots, event cursors, and operation outcomes in `@june/protocol`.
3. Build a local host in `@june/server` and a TypeScript client in `@june/client`.
4. Migrate the desktop preload and CLI to that client without changing the session model.
5. Prove the protocol from a second language before treating it as language-neutral.

The migration is complete when desktop and CLI can attach to the same live session through the shared client,
reconnect without an event gap, and render or ignore every canonical part without importing `@june/core`.
