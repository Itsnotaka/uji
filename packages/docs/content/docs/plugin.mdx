`@uji-ai/plugin` is what a plugin file imports: `definePlugin` and the types a plugin sees. It
re-exports them from `@uji-ai/core` and contains nothing else, so one process never holds two copies
of the plugin types. The host, registries, and loaders live in core. The contract and the reasoning
behind it are in the [design record](/docs/design#plugins); this page is the author's view.

Everything the model sees comes from a plugin. The harness owns no system prompt, tool list, or
skill catalog; the four built-ins below are plugins too, and yours replaces one by using its id.

```ts title="packages/plugin/examples/fast-mode.ts"
import { definePlugin } from "@uji-ai/plugin";

export function fastModePlugin(model) {
  return definePlugin({
    id: "fast-mode",
    async session(api) {
      // commands, settings, request patches
    },
  });
}
```

## What `session(api)` can do

`session` runs once per activation of your plugin against one session in one host process. Every
registration goes through the plugin's scope, so disposing the plugin removes all of it.

| Verb                                                                   | Kind       | What it is                                                                                                                                                                                                                                                                            |
| ---------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api.tools` `api.commands` `api.prompt` `api.resources` `api.settings` | contribute | `add((draft) => …)` registers a synchronous function over a draft. The registry replays every function over a fresh draft whenever the plugin set changes, in activation order. Later plugins can `update`, `delete`, or (for tools) `wrap` an earlier plugin's entry. No I/O inside. |
| `api.hook(name, handler)`                                              | intercept  | Returns a typed result the harness reads. Combining rules are fixed per hook; `before_drive` and `before_tool` fail closed, the rest contain failures and continue.                                                                                                                   |
| `api.on(type, listener)`                                               | observe    | Sees every harness event. Returns nothing the harness reads; a throw becomes a `handler_error` event.                                                                                                                                                                                 |
| `api.effect(setup)`                                                    | run        | Process-local I/O. Gets an `AbortSignal` that fires on dispose; a returned disposer is tracked.                                                                                                                                                                                       |
| `api.storage`                                                          | persist    | Session facts under `plugin:{id}:`. Durable, visible to every process on the session, in the log. One session only.                                                                                                                                                                   |
| `api.ask(request)`                                                     | ask        | `confirm`, `select`, or `input` rendered by the attached client. Today an in-memory compatibility path with a host timeout; durable asks are slice 7.                                                                                                                                 |
| `api.diagnostics` `api.plugins.list()` `api.options` `api.env`         | read       | Warn or error to the host; the plugin inventory; your manifest options; `{ cwd }`.                                                                                                                                                                                                    |

## Hooks

| Hook                | Sees                                               | May return                          | Combining rule                                                  |
| ------------------- | -------------------------------------------------- | ----------------------------------- | --------------------------------------------------------------- |
| `before_run`        | prompt, resources                                  | `{ messages }` to inject            | chained; each handler sees what earlier ones injected           |
| `before_drive`      | `operation: "run" \| "compaction" \| "navigation"` | nothing                             | a throw refuses the drive                                       |
| `before_run_end`    | runId, messages                                    | `{ followUp }`                      | last writer wins; the handler must terminate its own follow-ups |
| `transform_context` | messages, systemPrompt                             | replacements                        | chained                                                         |
| `before_request`    | model, step, attempt, streamOptions                | `{ streamOptions }` patch           | patches applied in order                                        |
| `before_payload`    | model, payload                                     | `{ payload }`                       | chained                                                         |
| `after_response`    | status, headers, message                           | `{ message }`                       | chained                                                         |
| `before_tool`       | toolCallId, toolName, args                         | `{ args }`, `{ block: { reason } }` | args chained; first block stops; a throw blocks                 |
| `after_tool`        | call, content, details, isError, usage             | field-wise patch, `terminate`       | field-wise chained                                              |

Every hook event also carries `head` and `runId`. Handlers must be re-entrant per step: a stateless
runner constructs them fresh each invocation, so anything that has to outlive a step goes to
`api.storage`, never a closure.

## Rules that follow from the session model

- **Storage is one session.** A value written through `api.storage` is a durable fact on that session
  and is what every other process reads. State that should follow the user across sessions is a host
  concern and arrives through `api.options`.
- **Settings have no cached value.** A `PluginSetting` is a label, a non-empty choice tuple, and
  `read`/`apply` over plugin storage. Clients re-read after applying. A choice may carry a `status`
  badge; leave it off for the off state.
- **Effects die with the process.** On a step-at-a-time host an effect runs and is aborted every
  invocation. Do not make it the only home of anything.
- **Failures are contained.** A throwing factory marks the plugin `failed` and keeps the previous
  version live; a throwing contribution is a diagnostic and the rest of the table still builds; a
  throwing listener is an event.

## Loading

The host decides where plugins come from. The TUI resolves built-ins, then `~/.uji/plugins`
(`user`), then `<cwd>/.uji/plugins` (`project`), and only reads the project directory after the
workspace is trusted.

- `foo.ts` and `foo/index.ts` are both the plugin `foo`. The default export must be a `definePlugin`
  value whose `id` is `foo`.
- A file that shares an id with a built-in replaces it in place.
- `.uji/uji.json` disables ids (`"-name"`) and sets `options` (`{ "id": "name", "options": … }`). It
  never lists plugins.
- Edits are picked up: a file's version is its mtime and size, and the host reactivates on change.
  `/reload` in the TUI does the same on demand.

## Split

| Package          | Role                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `@uji-ai/plugin` | Author surface: `definePlugin`, `Plugin`, `SessionApi`, hook, command, setting, and storage types          |
| `@uji-ai/core`   | `PluginHost`, `resolvePlugins`, `watchPluginDirectories`, `inlinePlugin`, `toolsPlugin`, builtins, storage |

Built-in factories are exported from `@uji-ai/core`. A user plugin with the same id replaces the
builtin:

| Factory              | Id              | Job                                                                                                         |
| -------------------- | --------------- | ----------------------------------------------------------------------------------------------------------- |
| `systemPromptPlugin` | `system-prompt` | The prompt body; other plugins add sections through `api.prompt` and the harness joins them                 |
| `contextFilesPlugin` | `context-files` | Loads project context files into the prompt                                                                 |
| `skillsPlugin`       | `skills`        | Catalogs `SKILL.md` folders into `resources` and the prompt; bodies load on demand                          |
| `toolsFsPlugin`      | `tools-fs`      | The seven coding tools with their replay policy; the only thing that puts `src/tools` in front of the model |

Worked examples live in `packages/plugin/examples/` (`fast-mode`, `question`).
