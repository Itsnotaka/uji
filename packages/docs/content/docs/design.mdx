This page is the design of `@uji-ai/core`: what the runtime is, the shape each part has, and the
behavior every host and client can rely on. When this page and another document disagree on a
contract, this page wins. **must** and **must not** are normative. What is built and what is not
is a question for the tree and its tests; this page describes the shape, not the status.

The measure for every section is the same: the fewest mechanisms that keep the promises below. A
feature that can be a projection over the log is a projection. A verb that can be two existing
verbs is not added. Where two mechanisms would do one job, this page picks one and names it.

## What core is

Uji core is a durable runtime for agent conversations. Three promises drive it:

- **It runs anywhere.** The same core runs inside an Electron main process, under a TUI, on a VM,
  and on stateless infrastructure such as a Cloudflare Worker or a Durable Object. A run is a
  function over stored state, so where it runs never changes what survives. A long-lived process
  is an optimization, not a requirement.
- **Any number of participants at once.** A session is not owned by whoever renders it. A phone,
  a web page, a desktop app, and a cloud job can all send into one conversation at the same
  moment, and none of them gets an error for trying.
- **Nothing is lost and nothing is rewritten.** Every message, tool call, head move, and run
  boundary is an immutable fact in one ordered log. Going back is moving a pointer, never
  deleting. A dead process leaves a resumable trail, not a half-finished conversation.

Four scenes are the acceptance tests for the whole design:

1. Three phones send at the same moment into an idle session. The store serializes the sends. One
   lands at the tip; the others queue to the run that claimed the head. One run drains all three
   in order. Nobody gets an error, nothing forks, and the transcript reads like three people in a
   room.
2. A run is killed while a tool executes. Another process finds the expired claim, takes it over,
   settles the half-done tool by its declared replay policy, and continues. The client watching
   notices only a pause.
3. A tool asks a question. The asking host exits. An hour later a phone answers. Whichever host
   observes the answer resumes the run and settles the call exactly once.
4. A serverless handler receives a message, runs one step inside the request, streams the result,
   and exits. The next request, or an alarm, runs the next step. No process outlives a step.

### Facts we accept

Each mechanism on this page answers a fact we cannot change. That is what keeps the mechanism
count low: there is one per fact, and a new mechanism needs a new fact.

| Fact                                                   | Mechanism                                                          | Section                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------ | --------------------------------------- |
| The process can die at any moment, or never existed    | Every uncertain effect is bracketed by two commits                  | [Runs](#runs)                           |
| Any process may be the one that continues a run        | A runner keeps nothing in memory across a step                     | [Many runners](#many-runners-one-store) |
| Writers race constantly                                | Admission never errors; contention exists only on run claims       | [Admission](#admission-is-open)         |
| Providers cache the context prefix                     | Mid-run context grows only at the tail; input queues to boundaries | [Admission](#admission-is-open)         |
| The outside world will not join a database transaction | Per-tool replay policy instead of impossible exactly-once          | [Runs](#runs)                           |
| A network client cannot hold object handles            | Every verb takes one flat object; ids ride inside it               | [The SDK](#the-sdk)                     |
| Users change their minds                               | History is a tree; a head is a movable pointer with a log          | [Heads](#heads-are-named-pointers)      |

### Roles

Six roles. One process can play several at once: the TUI plays all of them, a phone plays one.

| Role   | Is                                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| store  | The durable state: entries, records, heads, facts, claims. The only authority.                                                       |
| runner | Whatever code holds a run claim and executes steps. A hot loop on a laptop and an alarm handler in the cloud are both runners.       |
| host   | A process that composes core: opens a store, resolves plugins behind trust, supplies the stream function, and may volunteer runners. |
| client | Anything that calls SDK verbs and renders events. It keeps no state beyond a cursor.                                                 |
| plugin | Host-side code that decides what the model sees and can intercept a run.                                                             |
| schema | The shared types every boundary speaks.                                                                                              |

## The model, in git terms

Core's session model is git's model with messages in place of files. The correspondence is exact
enough to be the reading guide for the rest of this page.

| git                                     | core                                                                            |
| --------------------------------------- | ------------------------------------------------------------------------------- |
| object store                            | the session log: one ordered stream per session                                 |
| commit: immutable, names its parent     | entry: immutable, names its parent                                              |
| branch ref: a name pointing at a commit | head: a name pointing at an entry; `main` always exists                         |
| HEAD: which ref you are on              | the head name a client passes; client state, never a store register             |
| detached HEAD                           | reading at an entry with no head; sending needs a head, so create one there     |
| reflog: old, new, actor, reason         | head moves in the log: from, to, cause, actor; unconditional, never pruned      |
| index: staged, not yet committed        | the pending queue: admitted with an id, not yet in the tree                     |
| ref lock and compare-and-swap           | the run claim: a compare-and-swap with a fence and a TTL                        |
| worktree: one checkout of one branch    | a run: one head being advanced by one runner; one live run per head             |
| stack metadata: parent branch, base     | a head's parent head and base entry; a child session's parent link              |
| rebase and replay                       | carry-forward by summary: entries never move, a summary lands at the new base   |
| clone                                   | fork: copy a branch into a new session                                          |
| gc                                      | none: nothing is ever deleted                                                   |

Two places core is deliberately stricter than git. Git's reflog is off in bare repositories and
expires; core logs every head move, everywhere, forever, because the move log is the only undo and
there is no human at a terminal to reconstruct state from memory. Git serializes writers but not
readers, so a multi-ref update can be seen torn; core's store gives every read one snapshot.

## The log

A session is four kinds of state, all ordered by one per-session counter, `seq`:

- Write-once **entries**: the conversation tree, parent-linked.
- Append-only **records**: run bookkeeping, scoped to a head and a run.
- Mutable **heads**: named pointers into the tree, every move logged.
- Mutable **facts**: small key-values (session name, labels, plugin storage), every write logged.

Nothing mutates an entry or record after commit. Heads and facts are the only things that change,
and each change is itself a log item. Every value crosses the storage boundary through
`toJsonValue`, which rejects anything JSON cannot round-trip.

| Entry                                                   | Meaning                                                                                    |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `message`                                               | One user, assistant, or tool-result message.                                               |
| `compaction`                                            | A context checkpoint: portable summary and retained tail, plus optional provider material. |
| `branch_summary`                                        | What a path that was left was about, placed where the head landed.                         |
| `model_change`, `thinking_level_change`, `agent_change` | Run-input declarations, folded at run start.                                               |
| `custom`                                                | Product-defined. Core stores and replays it; clients render it.                            |

| Record               | Meaning                                                                          |
| -------------------- | -------------------------------------------------------------------------------- |
| `operation_started`  | A run began: its intent (run, compaction, navigation) and the folded run inputs. |
| `step_attempt`       | One provider call is about to happen.                                            |
| `retry_scheduled`    | A transient failure; the wake time is durable.                                   |
| `tool_started`       | Intent: this tool will run; its result lands at `resultEntryId`; replay policy.  |
| `tool_waiting`       | The call parked on purpose; recovery must not touch its reserved entry.          |
| `tool_reply`         | An answer admitted for a waiting call.                                           |
| `tool_wake_observed` | A wake pass that settled nothing; bounds what the next wake re-reads.            |
| `usage`              | Token usage for one cause.                                                       |
| `queue_enqueued`     | Input admitted behind a live run: a provisioned entry and its lane.              |
| `queue_consumed`     | A queued item entered the tree.                                                  |
| `queue_cancelled`    | Tombstone for an unconsumed item.                                                |
| `abort_requested`    | A durable abort the claimant honors at its next checkpoint or provider event.    |
| `operation_finished` | Terminal: completed, aborted, or failed.                                         |

The whole log is one typed stream, and that stream is the event system:

```ts
type LogItem =
  | { kind: "entry"; seq: number; entry: Entry }
  | { kind: "record"; seq: number; record: SessionRecord }
  | {
      kind: "head";
      seq: number;
      head: string;
      from: string | null;
      to: string | null;
      by: "append" | "move" | "create" | "delete";
      actor?: string;
    }
  | { kind: "fact"; seq: number; fact: string; value: JsonValue | undefined }
  | { kind: "claim"; seq: number; head: string; runId: string; state: "acquired" | "released" };
```

Why write-once plus one counter:

- Crash states are enumerable. A crash lands between transactions, never inside one, so recovery
  reads state instead of repairing it.
- Projections are rebuildable. Transcript, tree, usage, and directory views fold the log; they
  carry no authority and never write.
- Concurrency is cheap. Appends from different processes cannot conflict at the content layer;
  contention exists only at run claims.

Liveness is not content. A claim's acquire and release are log items because a client renders
them; a renewal is a register write and nothing else, so a heartbeat never consumes a `seq` and
never reaches a watcher. A client that wants liveness asks `runs.current`, which reads the claim.

## Heads are named pointers

A **head** is a named pointer to an entry: `head/{name} -> entryId | null`. Every session has
`main`. Creating a head at an entry is the fork. That is the entire feature, and everything else
on this page that looks like a feature (undo, branches, the tree view, stacks, subagents) is a
consequence of it.

A head carries five things and nothing else:

| Field    | Meaning                                                                              |
| -------- | ------------------------------------------------------------------------------------ |
| `name`   | The ref. `main` is created with the session; the rest are created by a verb.         |
| `tip`    | The entry it points at, or `null` for an empty branch. Called `leafId` in the store. |
| `parent` | The head it was created from, if any.                                                |
| `base`   | The parent's tip at creation. The stack edge (below).                                |
| `run`    | Derived, never stored: the claim on this head, if one is live.                       |

What a head deliberately does not carry: a configuration register (model, thinking level, and agent
are run inputs declared as entries on the branch), a state machine (the run claim is the state), a
pending-input list (pending input is session-scoped and drained by whichever run comes), and a
last-result register (a run's outcome is its terminal record).

### Moves and the move log

A head moves in exactly four ways, and every one is a log item carrying the previous tip, the new
tip, the cause, and the actor when known:

- **append**: an entry written through the head advances it. Concurrent appends through one head
  linearize; they never fork it.
- **move**: a deliberate re-point to an existing entry or to `null`. This is the revert, the undo,
  and the tree jump. There is no separate revert verb.
- **create**: a new head at an entry.
- **delete**: the name is dropped. The entries stay; the move log still names them.

The move log is the reflog. `head@{n}` in git is "the tip before the last n moves" here, and it is
how a client offers undo without core keeping an undo stack: undo is a move to the previous tip.
Moves **must** be logged unconditionally and **must not** be pruned.

### Where a client is

The head a client is on is the head name it passes to verbs, defaulting to `main`. It is client
state, not a store register, so two clients on one session can be on different heads and neither
can corrupt the other. A client may read at any entry (the branch ending there is a projection),
which is the detached state: reading is free, but sending requires a head, so a send from an old
point either moves a head there or creates one.

### Branching

Going back is a move, and the path that was left is kept, its parent links intact. The tree view
folds every entry into a forest and marks every head and the active path; a client renders it and
a user jumps. Moving an existing head away from a path leaves that path reachable through the move
log and the tree scan only, so a client that wants the path to stay findable and runnable creates
a head at its tip first. Two verbs, and a crash between them leaves nothing inconsistent.

A move executes as a **navigation run**: it claims the head exactly as compaction does, so nothing
re-points a head under a live run's feet, and it may leave a `branch_summary` entry at the
destination describing the path it left. Selecting a user message parks the head on that
message's parent and hands the message back for editing rather than replaying it.

```text
          e1 ─ e2 ─ e3 ─ e4           <- main was here; the path stays
                 └─ e5 ─ e6           <- main moved to e2 and continued
                 ^
                 base of review       <- head "review" created at e6 records parent main, base e6
```

### Stacks

A head created from another head records `parent` and `base`. That pair is what stacked-branch
tools keep beside each branch, and it answers the two questions a stack needs in constant time:

- **Is this branch stale?** `base !== parent.tip`. The parent moved on since the fork.
- **Which entries are mine?** Everything after `base` on my branch.

Entries are immutable and a model's replies were conditioned on the prefix they were written
under, so core never replays entries onto a new base the way `rebase` replays commits. Carrying a
branch forward is **restack by summary**, and it is the existing move verb: move this head to the
parent's tip with `summary`, which summarizes the entries after `base`, lands the summary at the
new tip, and sets `base` to it, all in one transaction. When the parent has only advanced and the
old base is still an ancestor of the new tip, `base` advances silently, the same self-heal
stacked tools use.

Stacks cross sessions too. A child session written by the `task` tool carries a durable parent
link (session, run, tool call, agent, depth). Its completion is delivered into the parent as an
ordinary admission, which is the whole of "sync" for a conversation stack.

### Fork into a new session

A fork copies the branch ending at an entry into a new session, keeping entry ids, so a copy can
be told from the original by session alone. It is `clone`, and it exists for the one case a head
cannot cover: a conversation that should stop sharing a log with its origin.

## The turn

The turn is the whole of the agent loop, and it does not loop.

```ts
runAgentTurn(context, config, emit, signal, streamFn): Promise<void>;
```

One assistant response is streamed, its tool calls are executed, and events are emitted. Whether
another turn follows is the caller's decision. The turn imports nothing from the store, the
runner, providers, or a Node host; it is a function over a message array, which is what makes the
same function usable in three places:

- **Under the runner**, once per durable step, over a branch projected from the log.
- **Without a store**, over an in-memory context: a title, a compaction summary, a branch
  summary, a script that wants one answer. This is the no-context path, and it is the same code.
- **In recovery**, over a synthetic context holding only the calls an interrupted run never
  started, so live and recovered settlements are built by one function and never drift.

The last message in the context must convert to a `user` or `toolResult` message, or the provider
rejects the request.

### The tool batch

Calls are validated and prepared in source order, and each call starts executing the moment its
own preparation passes. A later call's preparation (a policy hook, an approval) therefore never
holds an earlier call idle. This is a deliberate divergence from pi, which prepares every call
before starting any: that shape freezes the working lane on a prompt. Results are emitted in
source order regardless of completion order.

- A `length` stop fails every tool call in the message, because streamed arguments finalized by a
  salvage parser can validate and still be incomplete.
- A failed or aborted call settles carrying the last partial it reported: partial content after
  the error text, the partial's details and title when the error names none. A `ToolError` is the
  tool's own structured decision and is not amended.
- Every settlement, live or recovered, is built by one function.

## Runs

A **run** is an operation bracketed by `operation_started` and `operation_finished`, containing
step attempts, tool intents, settlements, and usage. Runs come in three intents: a conversation
run, a compaction, and a navigation.

### Claims

Execution rights come from a **run claim**: a store-level compare-and-swap binding one runner to
one run on one head, with a fence and a TTL. Claims are the only lock in the system. Readers,
senders, and runs on other heads never touch one.

```ts
interface RunClaim {
  readonly head: string;
  readonly runId: string;
  readonly ownerId: string;
  readonly fence: number;
  readonly expiresAtMs: number;
}
```

- Acquire is one upsert: insert, or take over a row whose TTL expired, incrementing the fence.
  Losing the race is a value, never an error; the loser's input is already admitted and the
  winner drains it.
- Every runner write runs inside one transaction that first renews the claim on
  `(ownerId, fence)`, ignoring expiry. Zero rows matched means fenced out, which is terminal for
  that claimant and aborts before touching data. Expiry exists so a successor can take over after
  a crash; it must not kill a claimant whose clock jumped while suspended.
- Release deletes only the claimant's own `(ownerId, fence)` row, so a stale owner can never
  release its successor.
- An expired claim on an unfinished run is an orphan. Any runner may claim it and resume.

The claim TTL is failover metadata. No public verb, claim, or runner option encodes a wall-clock
execution budget: hosts own budgets, process termination is the fence, and recovery works from
durable state alone.

### The step

The **step** is the durable unit of progress: one provider turn plus its tool batch, committed. A
runner that has committed a step may die; nothing is lost and any runner continues. A step reads
the run's state from the run's own records, makes one pass through a fixed pipeline, and commits.
The order is the contract:

| #   | Stage     | What happens                                                                                                                                 |
| --- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | abort     | A pending `abort_requested` ends the run `aborted`.                                                                                          |
| 2   | ceiling   | The agent's `steps` count, read off the run's records, ends the run `failed: steps`.                                                         |
| 3   | backoff   | An owed retry window is waited out; a process lost mid-wait resumes the wait.                                                                |
| 4   | drain     | Pending input for this boundary enters the tree, in `seq` order.                                                                             |
| 5   | project   | The branch becomes model context: the newest checkpoint plus everything after it.                                                            |
| 6   | compact   | Threshold compaction when the last usage report says the next request will not fit.                                                          |
| 7   | turn      | `runAgentTurn`. Nothing on this row touches the store except through the event sink.                                                         |
| 8   | settle    | Parked calls commit `tool_waiting` and the claim releases; a policy failure ends the run `failed: policy`; an overflowed request compacts once. |
| 9   | retry     | A transient provider error schedules a durable retry and yields; any other error or an abort ends the run.                                   |
| 10  | drain     | Steers that arrived during the turn enter the tree.                                                                                          |
| 11  | continue? | Tool results or new input mean another step; otherwise queued follow-ups are drained and, if any, another step.                              |
| 12  | finish    | No input left: `operation_finished`, remaining pending input applied, claim released, in one transaction.                                    |

### The effect sandwich

Every uncertain effect is wrapped in two commits:

```text
commit:  "about to do X; its output lands at provisioned id R"   <- intent
         do X                                                    <- the uncertain part
commit:  settled output at R + usage                             <- settlement
```

For tools, the intent is a `tool_started` record carrying the provisioned `resultEntryId`, the
effective arguments, and the tool's replay policy. It commits before the tool executes; settlement
is written exactly once, at that id, and a duplicate id is refused by the store.

The replay policy answers the one question recovery cannot: after a crash between intent and
settlement, did the tool run?

- `replay: "safe"`: run it again with the persisted arguments. Reading a file twice hurts nobody.
  At-least-once.
- `replay: "never"` (the default): do not run it again. Recovery settles the reserved entry with an
  error naming the interruption, so the model reads "outcome unknown" instead of a hole.
  At-most-once.

Exactly-once would need the outside world to join the transaction, and it will not. A settled
result is never touched again.

| Crash point                         | Recovery                                                      |
| ----------------------------------- | ------------------------------------------------------------- |
| before the intent commit            | previous state; the step runs as if nothing happened          |
| after the intent, before settlement | apply the replay policy                                       |
| after settlement                    | continue; never re-settle                                     |
| mid provider stream                 | the turn is re-taken; a partially billed stream is the price  |

An assistant turn commits `step_attempt` before the request and the message after it. A crash in
between leaves a branch whose tail still expects an answer, so the next step simply asks again.

### Wait and wake

A run does not have to hold a claim while it waits on the world. A tool parks by throwing
`ToolWait` from `execute`: the runner writes one `tool_waiting` record per parked call and
releases the claim without a terminal record. The run then consumes no process anywhere. The wake
input arrives as ordinary admission: an answer through `runs.reply`, a child session's completion,
a webhook-driven append. Whichever host observes it claims the run, calls the tool's `wake`, and
settles the reserved entry exactly once.

- The park carries no payload. A wake re-derives everything from the intent's validated arguments
  and ids derived from the session, run, and call.
- Admission treats a waiting run as live: sends queue to it and other writes defer, so mid-run
  context still grows only at the tail.
- The wake predicate is durable: a parked run resumes only when input newer than its last
  released claim has arrived, or an abort is pending. A host without the owning plugin leaves the
  wait alone; abort is the exit that works everywhere.

This one mechanism is the ask that outlives its process, the mid-run approval, the foreground
subagent, and the scheduled wake. Core carries no ask vocabulary: the pending tool call renders
the question, and the reply is a message the tool's `wake` absorbs.

### Retries

A transient provider failure commits `retry_scheduled` with the attempt and a `notBefore` time,
then yields the step. The wait is durable, so a process lost mid-backoff resumes the wait rather
than restarting the turn, and a step-at-a-time host schedules its re-entry from the record. The
failed turn stays in the tree as history and never reaches the retry. The retry budget resets on
any turn that settles without a provider error, so a long healthy run never exhausts it. Overflow
is classified before retry, so an oversized request compacts instead of retrying unchanged.

### Compaction

A `compaction` entry is a context checkpoint. Context projection starts at the newest one and
keeps everything after it; the transcript keeps everything, because compaction changes what the
model sees, not what happened. Every compaction carries a portable summary and retained tail, and
may carry opaque provider material bound to one provider, API, and model. Core passes the material
as `context.checkpoint` only when the next request targets exactly that triple; every other target
gets the portable projection. Both are written in one entry, so a later model switch never
depends on a failed oversized request to recover.

Compaction runs for three reasons: `manual`, as its own run; `threshold`, inside a run, when the
last usage report says the next request will not fit under the reserve; `overflow`, at most once
per run, when the provider rejects the request as too large. A `branch_summary` is not a
checkpoint: projection keeps everything before it and adds the summary as one message.

### Two runner shapes

- **Hot loop** (desktop, TUI, VM): claim once, execute steps in-process until the run finishes or
  waits, renew as it goes. Releasing between steps would read as an orphan to every other host.
- **Step-at-a-time** (Worker, queue consumer, alarm-driven Durable Object): claim or renew, read
  the run's state, execute one step, commit, schedule re-entry, exit. The TTL covers the gap.

Both have identical durable behavior because of one rule: **a runner must not require in-memory
state that outlives a step.** Drained positions, retry counts, compaction bookkeeping, and the
turn count are all derived from the run's records.

## Admission is open

Appending a message, an answer, or a custom entry requires no claim of any kind. The store
serializes concurrent appends and assigns `seq`. Rejecting a send because someone else is talking
**must not** happen at any layer. Session exclusivity is not something a sender can see.

Open admission does not mean mid-run insertion into the provider context. Across one run's
requests, context grows only at the tail, so admission has two dispositions, decided inside the
admit transaction by reading the head's claim:

```text
TX[
  if the caller's entryId already has a receipt:  return it, "duplicate"
  if no live or waiting run on the head:          write the entry at the tip, "placed"
  else:                                           write queue_enqueued { lane, entry }, "queued"
]
```

### Lanes

There is one pending record kind. A queued message and a deferred custom entry are the same thing:
a provisioned entry waiting for a boundary, with a lane.

| Lane    | Drains                                                    |
| ------- | --------------------------------------------------------- |
| `steer` | At the run's next checkpoint, before the next turn.       |
| `queue` | When the run would otherwise stop, starting another turn. |

- **Delivery is a property of the item, not a decision frozen at send.** A second
  `queue_enqueued` for the same entry moves it between lanes; the first record fixes its position
  and its id. Moving into `steer` with no live run is itself the wake.
- **Pending is a store query.** An item is pending when its latest record is not cancelled and
  its entry is not yet in the tree. The drain, the pending list, and the terminal sweep ask the
  store one question, so they cannot disagree.
- **Cancel** writes a tombstone. **Consumption** writes `queue_consumed` beside the entry.
- A drain takes one item per lane per boundary unless the host asks for all, so one-at-a-time
  delivery stays the default a model can follow.
- The terminal transaction applies whatever is still pending, including for an aborted run, so a
  write racing the end of a run is neither lost nor ordered after it.

### The working lane never freezes

The runner reads pending input only at checkpoints and never mid-batch, and admission never takes
a claim. A send during a tool batch commits in its own transaction; the tool batch runs on; the
two meet at the next boundary. The runtime is not one thread that alternates between user and
model. It is two lanes joined by a log.

### Who runs?

Ensuring a run exists is host territory. A host that called `attach()` follows the log and, when
a placement lands on an idle head or an orphan appears, races the claim. One host wins; the
losers do nothing. A thin client may have no runner at all; its send sits durable until a host
attaches. Opening, observing, or closing a session never contests a live claim: close is
claim-neutral, and a deliberate stop is `runs.abort` or `sessions.delete`.

Two additions ride admission because multiplayer input needs them. **Attribution**: entries and
send records carry an optional `origin` the host defines. Attribution, not authorization.
**Idempotency**: a caller-supplied `entryId` makes a retry return the first receipt instead of a
second message.

## Many runners, one store

The run is a worktree: one checkout of one head, advanced by one runner. Git allows one checkout
per branch and any number of worktrees over one object store, and core has the same rule at every
level.

- **Heads are independent.** Two runs on two heads of one session proceed concurrently with no
  coordination. Contention exists only at the claim of one head.
- **Sessions are independent.** A host serving many sessions holds one runner per claimed head,
  and a store holds any number of sessions.
- **Processes are interchangeable.** The same runner code in two processes points at different
  state because all state is in the store, exactly as one `git` binary serves every repository.
  Nothing a runner needs survives in memory across a step, so which process runs the next step
  is a scheduling choice, not a correctness question.
- **Takeover is by fence.** A successor increments the fence; the predecessor's next write dies
  before touching data. A second process can abort a run in flight by writing `abort_requested`;
  the claimant sees it at its next provider event or checkpoint.
- **Children are sessions.** A subagent is a child session with a durable parent link written
  before its first admission. Its ids derive from the parent session, run, and call, so a crashed
  spawn retried lands once. Foreground delegation is background delegation plus a wait.

## Deployment

Three placements, one runtime.

- **Embedded.** The host process is also the runner and the client: the TUI, the desktop's main
  process. The store is a file, `watch` is a store subscription, overlays stream in-process.
- **Server.** A long-lived host owns a store and volunteers runners; clients speak the wire.
- **Serverless.** No process outlives a request. The store is remote; a request is a runner.

### The request shape

The request-scoped runner is the shape stateless chat SDKs made familiar: a handler receives a
message, streams the answer, and exits. Core provides it without a second code path. The sketch:

```text
POST /sessions/{id}/messages          admit: placed | queued | duplicate
GET  /sessions/{id}/events?after=seq  durable items, then live items; seq is the cursor
POST /sessions/{id}/steps             claim, run one step, release: continue | waiting | finished
```

A handler that wants to answer inline admits, claims, and drives steps while the request lives,
streaming overlays on the same response. If the client disconnects, the run either continues
under a long-lived host or is resumed by the next step request or an alarm; the claim TTL covers
the gap. Reconnect is `after=seq`, so a resumable stream needs no stream id and no side store:
the log is the stream, and what a lost connection loses is intermediate animation frames, never
state.

### The wire

Three package names are reserved for it. `@uji-ai/protocol` is the SDK's wire definition and
nothing else: one route per verb, the verb's input object as the body, outcome unions as response
bodies, thrown errors as status codes, one SSE channel per session. `@uji-ai/server` binds one
host to it. `@uji-ai/client` is the first-party TypeScript client with reconnect-by-cursor built
in. The wire **must** be implementable from any language; a Swift app is a citizen of the
protocol, not a port of the TypeScript client.

### Backends

A backend implements `SessionRepo` and `SessionStorage` from `@uji-ai/core/store`. The contract a
backend must hold is short: one `seq` counter per session shared by every item kind; ids unique
and entries never updated or deleted; an append reads the tip and advances it in one atomic unit;
participant writes serialized by the store; run writes fenced by the claim; every read from one
snapshot. A conformance suite, not review, keeps a second backend honest.

## Events and views

Two event tiers, one contract.

- **Durable events are the log.** Log items are the replayable stream and `seq` is the cursor. A
  client that reconnects replays from its cursor and is complete with respect to durable state.
- **Ephemeral overlays reference the log.** Streaming deltas and tool progress name the
  provisioned entry they settle into. A client that missed them recovers the settled entry and
  lost only animation frames.

`watch({ afterSeq })` replays durable items, emits `synced`, then interleaves live items with
overlays, racing the two sources so a streaming turn renders in real time. Every committing write
publishes its items before the writing verb resolves, so no item is neither replayed nor
delivered. `sessions.snapshot` is the cold open: one read model at one `seq`, handed straight to
`watch`.

Projections are pure functions over the log, shipped beside the store so every client agrees:
transcript (entries to turns, tool calls paired with results, one incremental fold), tree (the
forest with every head and the active path), stacks (heads with parents and staleness), usage,
the context gauge, the session directory, and file changes folded from settled patches. Core also
ships the base presentation of any tool result, total over unknown tool names and custom types; a
client's per-tool renderer is refinement, never load-bearing. **The transcript must render,
completely and honestly, with zero plugins active.** If a renderer needs it, the tool settles it.

## Plugins

Everything the model sees comes from a plugin. The harness owns no system prompt, tool list, or
skill catalog; the built-ins are ordinary plugins a host lists first and a user or project plugin
replaces by id. A plugin is an id and one factory over a session API with two verbs:

- **Contributions** are declarative and synchronous: functions over a draft, replayed over a
  fresh draft in activation order whenever the plugin set changes. A later plugin may update,
  wrap, or delete an earlier entry, which is how a policy wraps `bash` without owning it.
  Registries: tools, commands, prompt sections, resources, settings, agents.
- **Hooks** return a result the harness reads, combined per hook in registration order:
  `transform_context` (chained replacement), `before_request` (patches over stream options),
  `before_tool` (continue, modify, reject, or error; fails closed), `after_tool` (field-wise
  patch), `before_compaction` (first provider material wins).

Tool-call policy has one boundary, `before_tool`. `reject` settles the call as a model-visible
error and the run goes on; `error` settles it the same way and then fails the run, because a
policy that could not decide must not read as one that allowed the call. `continue` cannot bypass
a later policy.

Activation is per session, per host process, and a stateless runner activates before its step and
disposes after it, so handlers **must** be re-entrant and cross-step memory goes to plugin storage,
which is session facts under the plugin's own prefix. Core does not check trust: a host **must
not** hand the resolver a project directory before the workspace is trusted, and that is the whole
gate.

## Agents

There is one entity, the **agent**, a declared record in the `agents` registry: id, `mode`
(subtractive over a default of `all`: `primary` withholds it from parents, `subagent` from the
user's picker), `hidden`, description, an optional model ref, a system layer, and a `steps`
ceiling. A subagent is not a type; it is an agent a parent may name. Configuration is declared,
never composed at run time: a parent selects an agent by name and hands it a prompt, and cannot
widen its model, prompt, or the policies over its tools, because none of those are arguments the
model passes. Which agent drives a run is a run input recorded in `operation_started` and
re-resolved from the running host's registry on resume.

Delegation is the `task` tool over a child session: create with the parent link, send the prompt
under derived ids, and either settle at once with the child's session id (`background`) or wait
for the child's terminal record. The child is composed without the `subagents` builtin, which is
the nesting limit. A model-facing background job settles through the log, never through a
process-local registry the model polls; a host-local live terminal is a separate, ephemeral,
human-facing service.

## The SDK

Four entry points, not one barrel:

```text
@uji-ai/core            createUji, Uji, the SDK types, the projections, and the turn for one-shot use.
@uji-ai/core/plugins    definePlugin, SessionApi, hook names, builtin plugins. Host-side authoring.
@uji-ai/core/store      SessionRepo, SessionStorage, the SQLite backend, step and drive. Hosts and backends only.
@uji-ai/core/views      The projections again, reachable without the Node graph.
```

Every verb takes exactly one argument, an object, and `sessionId` rides inside it. There is no
session handle, because a handle is the one thing a wire cannot carry. Every SDK type is a plain
interface or a `kind`-discriminated union, which is what makes the protocol a mechanical mirror.
Domain outcomes are values on each verb's own union; the only thrown errors are `UjiClosed` and
`UnknownSession`. "Someone is running" is not an error anywhere.

```text
createUji({ store, streamFn, models, model, plugins, env, thinkingLevel?, compaction?, streamOptions?, workspaces?, vcs? })

Uji
  sessions   create · get · snapshot · list · rename · delete · configure
  messages   send · cancel · redeliver · list · pending
  runs       current · abort · wait · reply · compact · context · changes
  heads      list · create · move · delete
  workspace  list · forget · vcs.status · vcs.diff
  provider   models.list · models.default
  plugins    list · commands.list · commands.run · settings.list · settings.apply · resources.list
  watch({ sessionId, afterSeq } | { sessionId, live: true })   AsyncIterable<SessionEvent>
  attach(options?)                                             host verb: volunteer this process as a runner
  setPlugins(plugins)                                          host verb: the resolved list changed
  close()
```

The reads that matter are two: `sessions.snapshot` for a cold open and `watch` for everything
after. The single reads (`messages.list`, `messages.pending`, `runs.context`) exist for a wire
that wants one cheap answer, and each is a projection the snapshot already contains. Every verb
that takes `head` honors it; `main` is the default, never the only value.

The outcome unions a client switches on:

```text
SendReceipt       placed | queued | duplicate
CancelOutcome     cancelled | already_consumed | not_found
RedeliverOutcome  redelivered | unchanged | already_consumed | not_found
ConfigureOutcome  applied | deferred | unknown_model | unknown_agent
RunInfo           live | orphaned | waiting
AbortOutcome      requested | not_running
WaitOutcome       idle | waiting
CompactOutcome    compacted | nothing_to_compact | failed
MoveOutcome       moved (restored?) | busy | not_found | aborted | failed
```

`busy` on a head move is the one place a client can see a live run as a reason for not doing
something, and it is the honest one: re-pointing under a run's feet would corrupt it.

### Events

```text
DurableEvent, each with seq
  message { entryId, turn }                                     projected, never a raw entry
  head_moved { head, from, to, by }
  run_started { runId, head, startedAt, operation, agent? }
  run_finished { runId, head, finishedAt, outcome }
  run_waiting { runId, head, toolCallId, toolName }
  claim { head, runId, state: acquired | released }
  queued { item } · queue_consumed { entryId } · queue_cancelled { entryId }
  compaction { entryId, summary } · name_changed { name } · synced

EphemeralEvent
  text_delta · reasoning_delta { entryId, contentIndex, delta }
  tool_progress { entryId, callId, progress }
  retry_scheduled { runId, attempt, maxAttempts, at, message } · retry_started { runId, attempt }
  compacting { runId, reason }
  plugins_changed { plugins } · diagnostic { owner, level, message }
```

A durable item becomes at most one event; items with no client meaning project to nothing.
`queued` is keyed by `entryId` and upserted: a second one is the item changing lanes. Ids are
branded (`SessionId`, `EntryId`, `RunId`, `HeadName`, `Seq`), created by the store, parsed at the
boundary, and named for their type in every field, so a value a verb returns is spelled the way
the next verb takes it.

## Invariants

The numbered list is the contract other documents and code comments cite by number. Numbers are
never reused.

Storage and session:

1. Entries and records are write-once; writing under an existing id is corruption.
2. One `seq` per session orders entries, records, head moves, claims, and facts. Backends must not
   shard counters.
3. Heads and facts are the only mutable state, and a head moves only by append-through, deliberate
   move, create, or delete.
4. A value crosses into durable storage only through `toJsonValue`.
5. Admission never requires a claim, never blocks on one, and never fails because one exists. Its
   two dispositions are decided atomically with the claim-state read.
6. Concurrent sends linearize; nothing forks a head except creating a head or moving one.
7. Admission is idempotent under a caller-supplied key.

Claims and runs:

8. At most one live claim per head; every run write is fenced by its claim; a fenced-out runner's
   transaction aborts before touching data.
9. An unfinished run with an expired claim is claimable by any runner. Resume settles unsettled
   intents by replay policy and never replays a settled effect.
10. The `tool_started` intent, with provisioned `resultEntryId` and replay policy, commits before
    the tool executes; settlement is written exactly once, at that id.
11. Every accepted run eventually commits `operation_finished`, including on runner failure,
    including when a different process finishes it.
12. A runner requires no in-memory state that outlives a step; everything the next step needs is
    in the log.
13. A waiting run holds no claim and consumes no process anywhere; its wake input arrives by
    admission and its settlement obeys invariant 10.

Turn and boundaries:

14. The turn imports nothing from runner, store, providers, or Node hosts; a stream function never
    throws, failing in-band by stop reason.
15. A `length`-stopped turn fails its whole tool batch.
16. Tool results are content parts end to end; adapters encode at request time.

Events and views:

17. The log is the durable event stream; `seq` is the only cursor; replay from a cursor is
    complete with respect to durable state.
18. Ephemeral overlays reference the provisioned entry they settle into; host notifications carry
    nothing durable and are re-derivable by a list call. No client state depends on having seen
    either.
19. Projections read the log and never write.

Policy:

20. Ported files change only within the recorded divergence classes; new behavior composes.
21. Extension failures are contained; extension capabilities degrade across hosts; project
    extension code never loads before trust.
22. No global mutable defaults in core; the stream function is injected.
23. No public verb, claim, or runner option encodes a wall-clock execution budget. The claim TTL is
    failover metadata; hosts own budgets, process termination is the fence, and recovery works
    from durable state alone.

Plugins:

24. Nothing reaches the model except through a plugin contribution. The harness owns no prompt,
    tool, or skill of its own; built-ins are plugins and are replaceable by id.
25. Contribution tables are a function of the activation list alone: replaying the same list over
    a fresh draft yields the same tables, and a rebuild never reads the previous table.
26. Plugin storage is session facts under the plugin's own prefix. A plugin cannot reach another
    plugin's keys, and a setting has no in-memory copy the log could contradict.

Agents:

27. An agent is one declared record from the `agents` registry. There is no separate subagent
    type; `mode` is subtractive over a default of `all` and never grants a capability. Built-in
    agents are contributions replaceable by id.
28. A parent selects an agent by name only. It never sets the child's model, prompt, or tools, and
    it cannot loosen the policies over them. A child composed without the `subagents` builtin is
    the nesting limit.
29. The driving agent is a run input recorded in `operation_started` and re-resolved from the
    running host's registry on resume; the head carries no agent register.
30. A model-facing background job settles through the durable log, never through a process-local
    registry the model queries. A host-local live terminal is a separate, ephemeral, human-facing
    service.

Presentation:

31. A settled tool result is self-contained: failure and abort settlements preserve the last
    reported partial, and no projection reads ephemeral history. Core projections and base
    presentation are total over unknown tools and custom types and never consult the plugin list.
    Per-tool renderers are client composition and are never load-bearing.

Heads and pending input:

32. Every head move is logged with its previous tip, its new tip, its cause, and its actor when
    known, unconditionally, and the move log is never pruned.
33. A head created from another records its parent and base; staleness is `base !== parent.tip`;
    a branch is carried forward by a summary at the new base, and no entry is ever rewritten or
    re-parented.
34. Pending input is one record kind with a lane, and "pending" is one store query every consumer
    shares.

## Open questions

1. **Long tools on stateless placements.** A bash command that outlives a request needs to run
   where a process lives and settle by admission. The wait mechanism covers it; the host wiring
   does not exist yet. Decide with the first remote backend.
2. **Durable streaming frames.** One compact frame per provider event in an auxiliary table keyed
   by the reserved entry id, deleted at settlement, would give cross-process observers token
   granularity through the store alone. The price is a write per event. Measure before paying.
3. **Records ledger growth.** Every record is kept forever for audit and replay. Revisit only when
   growth measurably hurts.
4. **Joining heads.** Restack by summary carries one branch onto another. A general join of two
   named heads stays deferred until a product needs one.
5. **Identity.** `origin` is attribution. ACL-scoped callers are host and protocol territory; the
   only core obligation is that `origin` is durable and hooks can read it.
6. **Host-scoped plugin storage.** Session facts are one session. Preferences that follow a user
   across sessions need a host-owned store on the session API; decide when a second plugin needs
   it.

## Lineage

The turn and the durability mechanics (the effect sandwich, provisioned ids, replay policy, one
`seq`) are ported from and tracked against pi, with one recorded divergence: the tool batch starts
each call as it is prepared instead of preparing every call first. The admission vocabulary
(`steer`, `queue`, `wait`, opaque cursors) follows OpenCode. The head model follows git (objects,
refs, reflog, worktrees, ref locks) and the stack metadata follows Graphite's open-source fork
charcoal (a parent branch and base revision per branch, staleness as one equality, restack from
the recorded base). Open admission, heads with a move log, run claims, and the step contract are
Uji's own. Ported files keep their `Based on` credit, and `THIRD-PARTY-NOTICES.md` lists every
upstream.
