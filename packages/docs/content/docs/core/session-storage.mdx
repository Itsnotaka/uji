A session exposes four kinds of ordered log item. **Entries** are write-once nodes that form a tree: each one records its `parentId`, so history branches instead of being rewritten. **Records** are a write-once, append-only ledger of what a lane did: a run started, a tool call was about to execute, a turn reported usage. **Lane moves** and **facts** are also appended to the log. The materialized lane leaf is overwritten in place for fast lookup; the session name is derived from the latest appended fact.

One per-session `seq` counter orders all four, so the whole session collapses to a single ordered log.

<Callout type="warn" title="The seq invariant">
  One counter per session, shared by entries, records, lane moves, and facts. `appendEntry` consumes
  two values (the entry, then the lane move it implies), `appendRecord`, `moveLane`, and `setName`
  consume one each. A backend that gives each table its own counter breaks `getLog`, which merges
  the four tables and sorts on `seq`, and every `afterSeq` cursor built on it.
</Callout>

## Entries

An entry is a node in the session tree. `EntryBase` supplies `type`, `id`, `seq`, `parentId`, and `timestamp`; each variant adds its own payload.

| `type`                  | Extra fields                           | Meaning                                                                                    |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------ |
| `message`               | `message: ResponseItem`                | One item of conversation: a user message, an assistant message, a tool call, a tool result |
| `model_change`          | `modelId: string`                      | The model in effect from this point down the branch                                        |
| `thinking_level_change` | `thinkingLevel: string`                | The thinking level in effect from this point down the branch                               |
| `custom`                | `customType: string`, `data?: unknown` | An application-defined node the harness does not interpret                                 |

Callers do not supply `parentId`, `seq`, or `timestamp`: the backend assigns them at append. What callers do supply is the `id`, which is why the provisioned shape exists:

```ts
type ProvisionedEntry<TEntry extends Entry = Entry> = TEntry extends Entry
  ? Omit<TEntry, "parentId" | "seq" | "timestamp">
  : never;
```

The conditional is there to distribute over the union. A bare `Omit<Entry, ...>` would keep only the keys every variant shares (`type` and `id`), so `ProvisionedEntry` with no argument, which is what `appendEntry` and `intent.initialMessages` take, would reject `message`, `modelId`, and `customType`.

Minting the id before the content is durable is what lets a caller reserve a slot: the harness writes a `tool_started` record naming `resultEntryId` before the tool runs, then appends the result entry under exactly that id. After a crash, a reserved id with no entry is an unsettled effect. See [the harness](./harness.mdx).

`appendEntry(entry, lane)` reads the lane's current leaf inside the write transaction, sets `parentId` to it, inserts the entry, then advances the lane to the new entry. A duplicate id is rejected with `SessionError("invalid_entry")`; entries are never updated.

## Records

A record is a lane-scoped ledger row. Every variant carries `RecordBase` (`id`, `seq`, `lane`, `timestamp`) plus the fields below. Every writer today is `AgentHarness`; storage itself writes none of them.

| `type`               | Extra fields                                                                                     | Written by                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `operation_started`  | `sourceLeafId`, `intent: { kind: "run", originalPrompt, initialMessages }`                       | `prompt()`, before the prompt entries are appended. The record's own `id` is the run id           |
| `step_attempt`       | `runId`, `step: "assistant"`, `attempt`                                                          | Every `turn_start` event. `attempt` counts turns in the run, not retries                          |
| `tool_started`       | `runId`, `toolCallId`, `toolName`, `effectiveArgs`, `resultEntryId`, `replay: "never" \| "safe"` | `beforeToolCall`, before the tool executes                                                        |
| `usage`              | `runId`, `cause: "assistant" \| "tool"`, `usage: TurnUsage`                                      | A `turn_end` with assistant usage or `tool_execution_end` with tool usage                         |
| `queue_enqueued`     | `queue: "steer" \| "followUp" \| "nextRun"`, `runId?`, `target: ProvisionedEntry<MessageEntry>`  | `steer()`, `followUp()`, `nextRun()`                                                              |
| `abort_requested`    | `runId`                                                                                          | `abort()`, committed before the `AbortController` is signalled                                    |
| `operation_finished` | `runId`, `outcome: "completed" \| "aborted" \| "failed"`, `error?`                               | The end of a run, whatever the outcome                                                            |
| `queue_cancelled`    | `entryId`                                                                                        | Nothing. Not built yet: the type exists and `drainQueue` honours it, but no public API writes one |

`NewRecord<TRecord extends LaneRecord = LaneRecord>` is `Omit<TRecord, "seq" | "timestamp">`, distributed over the union by the same conditional trick: the caller supplies the record `id` and `lane`, the backend stamps the rest.

### The run id a backend must denormalize

`RecordQuery.runId` filters on a run id that is not always a `runId` field. The SQLite backend derives it at insert time: for `operation_started` it is the record's own `id`, for every other variant it is `record.runId` when present, and `null` otherwise. A backend that indexes only a literal `runId` field returns nothing for `findRecords({ type: "operation_started", runId })` and breaks `findOpenOperations`.

## SessionStorage

Storage failures throw `SessionError` with a `code` of `not_found`, `invalid_entry`, or `storage`. They are not `Result`-typed; only the harness API uses `Result`.

| Method                        | Contract                                                                                                                                      | Ordering                  |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `getMetadata()`               | Returns `{ id, createdAt }`                                                                                                                   | no seq                    |
| `appendEntry(entry, lane)`    | Parents the entry on the lane leaf, inserts it, advances the leaf. Returns the completed `Entry`. Rejects a duplicate id with `invalid_entry` | Consumes two `seq` values |
| `appendRecord(record)`        | Inserts the record and returns it with `seq` and `timestamp` filled in                                                                        | Consumes one `seq`        |
| `getEntry(id)`                | The entry, or `undefined`. Absence is meaningful: it is how an unsettled tool effect is detected                                              | no seq                    |
| `getLeafId(lane)`             | The lane's current leaf, or `null` for an unknown or cleared lane                                                                             | no seq                    |
| `moveLane(lane, to)`          | Points the lane at an existing entry, or at `null` to start a new root. An unknown target is `not_found`                                      | Consumes one `seq`        |
| `getBranch(lane)`             | The path from the leaf to the root                                                                                                            | Oldest first              |
| `findEntries(query?)`         | All entries in the session, optionally filtered by `type` and capped by `limit`                                                               | Oldest first              |
| `findRecords(query)`          | `type` is required; `runId` and `afterSeq` narrow further                                                                                     | Oldest first              |
| `findOpenOperations(lane)`    | Every `operation_started` on the lane with no `operation_finished` naming it. Callers resume the first result                                 | Newest first              |
| `getLog(options?)`            | Entries, records, lane moves, and name facts merged into one `LogItem[]`, optionally after a `seq` cursor                                     | Ascending `seq`           |
| `getName()` / `setName(name)` | The session name, latest write wins. `setName` consumes one `seq`                                                                             | no seq                    |
| `close()`                     | Releases the writer lease. Idempotent                                                                                                         | no seq                    |

The intended invariant is at most one open operation per lane. Storage does not enforce it, and the current
`AgentHarness.prompt()` admission check has an asynchronous race before it marks the run active. More than one
result from `findOpenOperations` is therefore a reachable harness bug, not proof that the SQLite file itself is
corrupt. `resume()` currently takes the newest result and leaves any others open.

`LogItem` is a discriminated union on `kind`:

| `kind`   | Shape                         |
| -------- | ----------------------------- |
| `entry`  | `{ seq, lane, entry }`        |
| `record` | `{ seq, record }`             |
| `lane`   | `{ seq, lane, leafId }`       |
| `fact`   | `{ seq, fact: "name", name }` |

## SessionRepo and SessionSearch

`SessionRepo` is the session factory. It has exactly three methods.

| Method             | Behaviour                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `create(options?)` | Creates a session, optionally with your own `id`, and returns it already claimed for writing. A colliding id throws `storage` |
| `open(id)`         | Opens an existing session and claims it. An unknown id throws `not_found`                                                     |
| `list()`           | `SessionMetadata[]` for every session in the repo, `ORDER BY created_at, id`: oldest first, so `.at(-1)` is the newest        |

`SqliteSessionRepo` adds two methods the interface does not declare: `searchEntries` (from `SessionSearch`, below), and `close()`, which closes every session it handed out and then the database handle itself. The examples on this page call `repo.close()` for that reason; a session's own `close()` only releases that session's writer lease.

Not built yet: there is no `delete`, no `fork`, and no way to remove a session or an entry. Nothing in the storage layer ever deletes a row.

`SessionSearch` is a separate interface, implemented by the repo rather than by a session, because the index spans every session in the file:

```ts
interface SessionSearch {
  searchEntries(
    text: string,
    options?: { limit?: number; type?: Entry["type"] },
  ): Promise<SessionSearchHit[]>;
}
```

A hit is `{ sessionId, entryId, timestamp, snippet, score }`, and **lower `score` ranks better**: results come back already sorted ascending.

## The SQLite backend

`SqliteSessionRepo` is the only implementation. It uses `node:sqlite`, so it needs a Node build with `node:sqlite` available; `@june/core` ships TypeScript sources with no build step.

```ts
import { SqliteSessionRepo, type SessionRepo, type SessionSearch } from "@june/core";

const repo: SessionRepo & SessionSearch = new SqliteSessionRepo("./.june/sessions.db");

const session = await repo.create();
const { id } = await session.getMetadata();
await session.setName("refactor the parser");

for (const meta of await repo.list()) {
  console.log(meta.id, new Date(meta.createdAt).toISOString());
}

await session.close();
console.log(id);
```

Appending is the same two calls the harness makes, with the id chosen up front:

```ts
import { newId, SqliteSessionRepo, type MessageEntry, type ProvisionedEntry } from "@june/core";

const repo = new SqliteSessionRepo("./.june/sessions.db");
const session = await repo.create();

const prompt: ProvisionedEntry<MessageEntry> = {
  type: "message",
  id: newId("e"),
  message: { role: "user", content: "list the failing tests" },
};

const entry = await session.appendEntry(prompt, "main");
console.log(entry.parentId, entry.seq); // null 1

await session.appendRecord({
  type: "operation_started",
  id: newId("run"),
  lane: "main",
  sourceLeafId: null,
  intent: {
    kind: "run",
    originalPrompt: [{ role: "user", content: "list the failing tests" }],
    initialMessages: [prompt],
  },
});

console.log((await session.getLog()).map((item) => item.kind));
// [ 'entry', 'lane', 'record' ]

await session.close();
await repo.close();
```

### One file, every session

The path you pass is a single database holding all sessions, keyed by `session_id`. That is what gives search one index across sessions, and it means opening a repo twice on the same path opens the same data. On first use the repo creates the parent directory and sets `journal_mode=WAL`, `synchronous=FULL`, and `busy_timeout=5000`.

| Table           | Key                                            | Holds                                                                                             |
| --------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `sessions`      | `id`                                           | `created_at` and `next_seq`, the session's single counter                                         |
| `entries`       | `(session_id, id)`, unique `(session_id, seq)` | `parent_id`, `lane`, `type`, `timestamp`, and the JSON payload. Keeps its rowid for the FTS index |
| `records`       | `(session_id, id)`, unique `(session_id, seq)` | `lane`, `type`, denormalized `run_id`, `timestamp`, JSON payload                                  |
| `lanes`         | `(session_id, lane)`                           | `leaf_id`: the current leaf, overwritten in place                                                 |
| `lane_moves`    | `(session_id, seq)`                            | Every leaf change, so `getLog` can replay lane movement                                           |
| `facts`         | `(session_id, seq)`                            | One row per `setName`; `getName` reads the highest `seq`                                          |
| `writer_leases` | `session_id`                                   | `owner_id`, `fence`, `expires_at_ms`                                                              |
| `entries_fts`   | fts5 virtual                                   | Trigram index over `entries.payload`, external-content, insert-only trigger                       |

Every writing transaction opens with `BEGIN IMMEDIATE`. Each one reads `next_seq` before writing it, and a deferred transaction takes a read snapshot it may fail to upgrade: a failure `busy_timeout` cannot rescue, because waiting never refreshes a stale snapshot.

Not built yet: there is no schema version stamp and no migration path. Changing the schema means the existing file is on its own.

### Search

`searchEntries` runs an fts5 trigram `MATCH` against the entry JSON and joins back to `entries`.

- Queries shorter than three characters return `[]`: the trigram tokenizer cannot match them.
- Your text is wrapped in one quoted FTS string, so it is never parsed as query syntax.
- `options.type` filters on the entry type; `options.limit` defaults to 20.
- `snippet` is a 12-token excerpt with `…` as the ellipsis; `score` is `bm25`, ascending.

Because the index is insert-only, it stays correct only as long as entries stay write-once.

<Callout type="warn" title="Search indexes the serialized payload">
  The FTS trigger receives raw entry JSON, not a projection of user-visible text. Image parts can
  put base64 in the index, and reasoning or provider-specific fields can become searchable. Before
  search is a public host feature, it needs an explicit text projection with privacy and size rules
  (`GAP-C10`).
</Callout>

### The writer lease

One writer per session, enforced. WAL happily interleaves writers from several processes, which is exactly what the model forbids, so `create` and `open` claim a fenced, expiring lease before returning a session.

<TypeTable
  type={{
    leaseTtlMs: {
      description: "How long a claim stays valid without renewal",
      type: "number",
      default: "30000",
    },
    heartbeatIntervalMs: {
      description:
        "Idle renewal cadence. Must be positive and strictly less than leaseTtlMs, or the constructor throws RangeError",
      type: "number",
      default: "10000",
    },
  }}
/>

The mechanics:

| Event             | What happens                                                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `create` / `open` | Upserts a lease row. The upsert only applies when no lease exists or the current one has expired; otherwise it throws `storage` with `Session already has an active writer`                                                                                              |
| Takeover          | An expired lease is replaced with a new `owner_id` and an incremented `fence`                                                                                                                                                                                            |
| Every write       | Renews the lease inside the same transaction, matching on `(owner_id, fence)` and requiring it to be unexpired. Zero rows matched means the write dies before touching data and the instance throws `Writer lease lost` from then on. Reopen through the repo to recover |
| Heartbeat         | An unref'd timer renews while the session is open but idle, so an expired lease is real evidence the owner is gone                                                                                                                                                       |
| `close()`         | Deletes the lease row, matching on `(owner_id, fence)` so a stale owner cannot release its successor                                                                                                                                                                     |

Two consequences worth holding onto. A lost lease is terminal for that `SqliteSessionStorage`
instance: there is no re-acquire. Closing a storage releases its lease, rejects later reads and
writes with `Session is closed`, and removes the storage from the repository's set of open handles.
`repo.close()` closes whatever handles remain before closing the shared database.

`SqliteSessionStorage` is fully synchronous behind `Promise.resolve` wrappers. The async signatures are contract, not concurrency.

## Writing a backend

The storage test suite is `packages/core/test/session-backends.test.ts`, and it constructs `SqliteSessionRepo` directly rather than taking a repo as a parameter. There is no backend-generic conformance harness: a second backend needs its own copy of these cases. They are worth copying, because they pin the contract:

**Round trip.** The first entry has `parentId: null`; the second parents on the first; `seq` strictly increases. After `close()` and `open(id)`: metadata `id` survives, `getLeafId("main")` is the last appended entry, `getBranch("main")` is oldest first, `getEntry(a.id)` deep-equals the value `appendEntry` returned, and `getName()` returns what `setName` wrote.

**One counter.** After two entries, one record, and one `setName`, `getLog()` returns exactly `["entry", "lane", "entry", "lane", "record", "fact"]`: seqs ascending, no duplicates.

**Run-id denormalization.** `findRecords({ type: "operation_started", runId: "run_1" })` finds the record whose own `id` is `run_1`.

**Open operations.** `findOpenOperations("main")` reports a started run after a reopen, and returns `[]` once an `operation_finished` naming that `runId` is appended.

**Forking.** `moveLane` to an ancestor, then append: the new entry parents on the move target, `getBranch` follows the new path, the abandoned entries stay readable with their `parentId` intact, and `findEntries()` still returns all four in append order with `limit` honoured. `moveLane` to an unknown id rejects with `Entry not found`.

**Write-once.** Appending the same entry id twice rejects with `already exists`.

**Lease.** A second `open` of a live session rejects with `active writer`, and succeeds after `close()`. An expired lease can be taken over: the successor sees the prior history and can write, and the stale owner's next write rejects with `lease lost`. The heartbeat pushes `expires_at_ms` past the original TTL on an idle session. A `heartbeatIntervalMs` not below `leaseTtlMs` throws `RangeError` from the constructor.

**Search.** A phrase finds its entry across sessions with the right `sessionId` and `entryId` and a snippet containing the term; a mismatched `type` filter returns `[]`; a two-character query returns `[]`; `limit` is honoured.

Beyond the test, four properties a passing backend still has to hold:

1. One counter per session, shared by all four row kinds. `appendEntry` takes two values, everything else takes one.
2. Ids are unique per session and entries are never updated or deleted.
3. `appendEntry` reads the leaf and advances it in the same atomic unit; a lane leaf moves only by append or `moveLane`.
4. Concurrency is your problem to exclude. `SessionStorage` has no multi-write transaction (`appendEntry` and `appendRecord` each commit alone), so a second writer produces interleaving the model does not define.

The suite does not construct `AgentHarness`, inject failures between its commits, or race lifecycle calls. It
therefore proves the SQLite primitives above, not the harness's end-to-end durability contract.

## Not built yet

- SQLite is the only backend. There is no in-memory backend and no JSONL backend; the JSONL storage that predated it was removed.
- No batched write. Accepting a run is several separate commits, and recovery repairs the gaps by re-probing rather than by making them impossible.
- No schema version, no migrations.
- No deletion of any kind: no `SessionRepo.delete`, no `fork`, no compaction, no branch pruning.
- No branch index. `getBranch` walks parent pointers through a recursive CTE on every call.
- No runtime decoder validates entries or records before persistence; TypeScript interfaces disappear at runtime, and `custom.data` is intentionally `unknown`.
- `newId(prefix)` retains only eight hexadecimal UUID characters after the prefix. That is a small durable identity space for a long-lived or distributed host.
- Closed storage objects stay referenced by `SqliteSessionRepo` until the repository itself closes.
- Search indexes raw entry JSON instead of a bounded, user-visible text projection.
