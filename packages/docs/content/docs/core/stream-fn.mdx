A `StreamFn` is the only thing the agent loop knows about models. It takes a context and per-turn
options, performs one assistant turn, and resolves with an `AssistantTurn`.
`packages/core/src/agent-loop.ts` imports no provider code; `createProviderStreamFn` in
`packages/core/src/stream-fn.ts` is the single file in `@june/core` that does. There is no default
registry: every loop or harness composition receives its `StreamFn` explicitly.

```ts
type StreamFn = (context: LlmContext, options: StreamFnOptions) => Promise<AssistantTurn>;
```

## The contract: never throw

A `StreamFn` must not throw or reject for a request, model, or runtime failure. It encodes the failure in its resolved value instead.

<Callout type="error" title="The loop does not wrap streamFn in try/catch">
`streamAssistantTurn` awaits `streamFn(...)` directly. A rejection propagates out of `runAgentLoop` / `runAgentLoopContinue`, past `turn_end` and `agent_end`, so neither event is emitted for the failed turn and no caller-visible turn is recorded. Inside [the harness](./harness.mdx) the throw is caught one level up and reported as `RunOutcome { kind: "failed", error: { code: "harness" } }` instead of the intended `code: "stream"`.
</Callout>

`AssistantTurn.stopReason` is what the loop switches on.

| stopReason  | Meaning                        | What the loop does                                                                                             |
| ----------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `"stop"`    | The turn finished normally     | Executes any `function_call` items, then continues                                                             |
| `"length"`  | The output hit the token limit | Fails every tool call in the turn with a synthetic error result, executes none of them, and takes another turn |
| `"error"`   | The request or stream failed   | Emits `turn_end` with empty `toolResults`, then `agent_end`, and returns                                       |
| `"aborted"` | The signal was aborted         | Same as `"error"`: `turn_end`, `agent_end`, return                                                             |

Two consequences worth stating plainly:

- `errorMessage` is the only channel for the failure text. The harness copies it into `HarnessState.errorMessage` on `turn_end` and into `OperationError.message` with `code: "stream"`.
- Abort only ends a run because the `StreamFn` reports it. The loop never polls `signal` between turns, so a `StreamFn` that ignores `options.signal` produces a run that cannot be stopped mid-turn.

### Deltas become `message_update`; items become history

`onDelta` is supplied by the loop and does exactly one thing: it pushes `emit({ type: "message_update", delta })` onto an array of promises. Those promises are awaited after `streamFn` resolves, so a slow event sink cannot stall your stream, and every `message_update` for a turn has settled before `message_start` is emitted for the turn's items.

Deltas are display-only. Nothing the loop keeps is derived from them. Only `AssistantTurn.items` is pushed into `context.messages`, emitted as `message_start` + `message_end`, and appended to the array `runAgentLoop` returns. The harness ignores that return value and writes its entries from the `message_end` events instead.

Text you stream through `onDelta` must also appear in the items you return, or it is lost when the turn ends.

## createProviderStreamFn

`createProviderStreamFn` adapts an `@june/ai` provider block plus credentials into a contract-honoring `StreamFn`.

<TypeTable
  type={{
    provider: {
      description:
        "The provider block. Supplies api, baseUrl, defaultModel, defaultEffort, and auth",
      type: "Provider",
      required: true,
    },
    auth: {
      description: "Static request auth, or a credential store to re-resolve from on every call",
      type: "ModelAuth | { store: CredentialStore }",
      required: true,
    },
    sessionId: {
      description:
        "Stable per-session id. Becomes prompt_cache_key on every request, and the session-id / x-client-request-id headers on the codex dialect",
      type: "string",
      required: false,
    },
  }}
/>

The two auth modes differ only in when credentials are read.

| Mode                                                   | Resolution                                                                  | Use when                                                                                              |
| ------------------------------------------------------ | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `auth: { apiKey, headers?, baseUrl? }` (a `ModelAuth`) | Read once, at `createProviderStreamFn` time. Used verbatim on every request | The credential is a static key you already hold, e.g. from an env var                                 |
| `auth: { store }`                                      | `resolveProviderAuth(provider, store, { signal })` runs on every call       | Anything OAuth-backed. The access token can rotate mid-session and the next turn picks up the new one |

The discriminator is the literal `store` key: the returned function checks `"store" in auth`.

Per call, in order:

1. Resolve auth. In store mode, `resolveProviderAuth` returning `undefined` produces `{ items: [], stopReason: "error", errorMessage: "No credentials for provider <id> — log in first" }`.
2. Pick the effort: `options.thinkingLevel ?? provider.defaultEffort`.
3. Call `streamResponses` with `model: options.model ?? provider.defaultModel`, `instructions: context.systemPrompt`, `input: context.messages`, `tools: context.tools`, plus `sessionId`, `signal`, and `onDelta` passed straight through.
4. Return `{ items, stopReason, usage }` from the result.

Any throw from steps 1–3 (a failed refresh, a non-2xx response, a `response.failed` event, an aborted fetch) is caught and returned as `stopReason: options.signal?.aborted === true ? "aborted" : "error"` with `errorMessage` set from the error.

### thinkingLevel and the reasoning field

`ThinkingLevel` has one member, `"off"`, that `ReasoningEffort` does not. `createProviderStreamFn` maps it to `undefined`, and `buildBody` in `packages/ai/src/api/responses.ts` only adds `reasoning: { effort }` when the effort is defined. So:

| `options.thinkingLevel` | Effort sent                                                       | Request body                      |
| ----------------------- | ----------------------------------------------------------------- | --------------------------------- |
| omitted                 | `provider.defaultEffort` (`"medium"` for both built-in providers) | `reasoning: { effort: "medium" }` |
| `"off"`                 | none                                                              | no `reasoning` field at all       |
| `"minimal"` … `"max"`   | that value                                                        | `reasoning: { effort: <value> }`  |

### Wiring one up

```ts
import { defaultProviders, FileCredentialStore, getProvider } from "@june/ai";
import { createProviderStreamFn } from "@june/core";

const store = new FileCredentialStore();
const provider = getProvider(defaultProviders(), "openai-codex");

const streamFn = createProviderStreamFn({
  provider,
  auth: { store },
  sessionId: "2026-08-14T09-12-03.000Z-s_1a2b3c4d",
});
```

`defaultProviders()` returns `[openaiCodexProvider(), openaiProvider()]`. `getProvider(providers, id)` throws `Unknown provider: <id>` when the id is not in the list: that throw happens at wiring time, outside the `StreamFn`, so it does not violate the contract.

Static auth skips the store entirely:

```ts
import process from "node:process";
import { openaiProvider } from "@june/ai";
import { createProviderStreamFn } from "@june/core";

const streamFn = createProviderStreamFn({
  provider: openaiProvider(),
  auth: { apiKey: process.env["OPENAI_API_KEY"] ?? "" },
});
```

## @june/ai in brief

`@june/ai` holds provider blocks, credential storage, auth resolution, and one streaming client. It does not import `@june/core`.

### Provider

A provider block bundles the auth methods, the transport, and the model list, because in this design the credential decides the transport: a ChatGPT OAuth token routes to the codex backend, an API key to the platform API.

### Credentials

Two stored shapes, one per provider id:

| Type               | Fields                                                                | Notes                                                                                          |
| ------------------ | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `ApiKeyCredential` | `{ type: "api_key"; key?: string }`                                   | `key` may be absent, which means "configured, but resolve from ambient sources"                |
| `OAuthCredential`  | `{ type: "oauth"; access; refresh; expires }` plus an index signature | `expires` is epoch ms. The codex flow stores an extra `accountId` through that index signature |

`ModelAuth` is the request-side shape, not a stored shape: `{ apiKey?, headers?, baseUrl? }`. The rule stated in `packages/ai/src/auth/types.ts` is that if a value cannot be expressed as one of those three fields, it is provider config, not auth.

`modify` being the only write path is what makes token refresh safe: `resolveProviderAuth` performs the refresh _inside_ `modify`, so two concurrent turns cannot both burn the same refresh token.

`FileCredentialStore` is the shipped implementation. It stores `auth.json` at `JUNE_HOME`, or `~/.june` when that is unset, writing the file `0600` under a `0700` directory, and serializes `modify`/`delete` per provider id through a promise chain. Note that `read` and `list` are not serialized: they re-read the file each time.

### resolveProviderAuth precedence

A stored credential owns the provider. Ambient sources are consulted only when nothing is stored.

| Stored credential | Behavior                                                                                                                                                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type: "oauth"`   | Requires `provider.auth.oauth`, otherwise throws. Refreshes inside `store.modify` when `expires - Date.now() < minOAuthValidityMs` (default 5 minutes), then returns `{ auth: await oauth.toAuth(credential), source: "OAuth" }` |
| `type: "api_key"` | `provider.auth.apiKey?.resolve({ env, credential })`                                                                                                                                                                             |
| none              | `provider.auth.apiKey?.resolve({ env })`                                                                                                                                                                                         |

The return is `AuthResult | undefined`; `undefined` means "not configured". `source` is a human-readable label for status UI: `openaiProvider` returns `"stored key"` for a stored key and `"OPENAI_API_KEY"` when it falls back to the env var. `ResolveOptions` lets you override `env` and `minOAuthValidityMs` and pass a `signal`, though `createProviderStreamFn` only passes `signal`.

### AuthInteraction

Login flows never touch a terminal or a window. They call two callbacks, so the same flow code serves a CLI, a desktop app, or a test.

| Member           | Shape             | Purpose                                                                                                    |
| ---------------- | ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `prompt(prompt)` | `Promise<string>` | Ask for input. `text`, `secret`, `select` (resolve with the option `id`), `manual_code`. Rejects on cancel |
| `notify(event)`  | `void`            | One-way status: `info`, `progress`, `auth_url`, `device_code`                                              |
| `signal`         | `AbortSignal`     | Aborts the whole flow. `AuthPrompt.signal` aborts one pending prompt                                       |

`ProviderAuthInteraction` is `AuthInteraction` with `signal` required; that is what `login` implementations receive.

```ts
import { createInterface } from "node:readline/promises";
import process from "node:process";
import { defaultProviders, FileCredentialStore, getProvider } from "@june/ai";
import type { ProviderAuthInteraction } from "@june/ai";

const provider = getProvider(defaultProviders(), "openai-codex");
const oauth = provider.auth.oauth;
if (oauth === undefined) throw new Error(`${provider.id} has no oauth auth`);

const interaction: ProviderAuthInteraction = {
  signal: AbortSignal.timeout(5 * 60_000),
  async prompt(prompt) {
    const rl = createInterface({ input: process.stdin, output: process.stdout });
    try {
      if (prompt.type === "select") {
        for (const option of prompt.options) console.log(`  ${option.id}: ${option.label}`);
      }
      return await rl.question(`${prompt.message} `);
    } finally {
      rl.close();
    }
  },
  notify(event) {
    if (event.type === "auth_url") console.log(`Open ${event.url}`);
    else if (event.type === "device_code")
      console.log(`Enter ${event.userCode} at ${event.verificationUri}`);
    else console.log(event.message);
  },
};

const store = new FileCredentialStore();
await store.modify(provider.id, () => oauth.login(interaction));
```

`openaiCodexOAuth.login` first prompts `select` with the options `browser` and `device_code`. The browser flow starts a PKCE authorization, listens on `http://localhost:1455/auth/callback`, and races that callback against a `manual_code` prompt where the user can paste the code or the full redirect URL; whichever settles first cancels the other. The device-code flow polls `https://auth.openai.com/api/accounts/deviceauth/token`, backing off five seconds per HTTP 429, and gives up after 15 minutes. Both flows are Node-only: the browser one starts a `node:http` server.

## The codex-responses dialect

`streamResponses` in `packages/ai/src/api/responses.ts` speaks both dialects from one code path. The differences are the URL suffix and four codex-only headers.

| Piece                               | `responses`         | `codex-responses`                              |
| ----------------------------------- | ------------------- | ---------------------------------------------- |
| URL                                 | `${base}/responses` | `${base}/codex/responses`                      |
| `OpenAI-Beta`                       | not sent            | `responses=experimental`                       |
| `originator`                        | not sent            | `june`                                         |
| `session-id`, `x-client-request-id` | not sent            | both set to `sessionId`, when one was supplied |

`base` is `(auth.baseUrl ?? request.baseUrl)` with a trailing slash stripped, so a `ModelAuth.baseUrl` from a credential wins over the provider block. Headers are built in this order: `content-type: application/json`, `accept: text/event-stream`, `authorization: Bearer <auth.apiKey>` when an api key is present, then every entry of `auth.headers`, so a credential's headers can overwrite the authorization header. `openaiCodexOAuth.toAuth` uses this to send `{ apiKey: credential.access, headers: { "chatgpt-account-id": accountId } }`, where `accountId` comes from the stored credential or, failing that, from `getAccountId(credential.access)` decoding the `https://api.openai.com/auth` claim out of the JWT.

The request body is identical for both dialects:

```json
{
  "model": "...",
  "instructions": "...",
  "input": [],
  "tools": [],
  "tool_choice": "auto",
  "parallel_tool_calls": true,
  "store": false,
  "stream": true,
  "include": ["reasoning.encrypted_content"]
}
```

plus `prompt_cache_key: sessionId` when a `sessionId` was passed, and `reasoning: { effort }` when an effort was passed.

### Items come from output_item.done

The codex backend sends an empty `output` array on `response.completed`, so `streamResponses` accumulates items from `response.output_item.done` events as they arrive and only falls back to `response.output` when it collected nothing. The platform API emits `output_item.done` too, so one rule covers both.

| SSE event                                    | Handling                                                                                                                                                                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `response.output_text.delta`                 | `onDelta({ kind: "text", text: delta })`                                                                                                                                                                         |
| `response.reasoning_summary_text.delta`      | `onDelta({ kind: "reasoning", text: delta })`                                                                                                                                                                    |
| `response.output_item.done`                  | Push `item` onto the collected items                                                                                                                                                                             |
| `response.completed` / `response.incomplete` | Resolve. `stopReason` is `"length"` when `incomplete_details.reason === "max_output_tokens"`, otherwise `"stop"`. `usage` is mapped from `input_tokens` / `output_tokens` / `total_tokens`, each defaulting to 0 |
| `response.failed` / `error`                  | Throw `"<model>: <message>"`                                                                                                                                                                                     |
| stream ends first                            | Throw `"<model>: stream ended without response.completed"`                                                                                                                                                       |

`ResponsesResult.stopReason` is only ever `"stop"` or `"length"`. `"error"` and `"aborted"` are produced by the wrapper in `@june/core`, never by the client.

## Write your own StreamFn

Any function matching the type works. The three rules are: catch everything, distinguish abort from error using `options.signal`, and return the model's output as `ResponseItem`s.

```ts
import type { AssistantTurn, StreamFn } from "@june/core";
import type { ResponseItem } from "@june/schema";

/** Whatever client you are adapting. */
interface ChatEvent {
  type: "text" | "done";
  text: string;
  truncated?: boolean;
  inputTokens?: number;
  outputTokens?: number;
}

interface ChatClient {
  stream(input: {
    model: string;
    system: string;
    messages: ResponseItem[];
    signal?: AbortSignal;
  }): AsyncIterable<ChatEvent>;
}

export function createChatStreamFn(client: ChatClient): StreamFn {
  return async (context, options): Promise<AssistantTurn> => {
    try {
      const items: ResponseItem[] = [];
      let stopReason: AssistantTurn["stopReason"] = "stop";
      let usage: AssistantTurn["usage"];

      for await (const event of client.stream({
        model: options.model ?? "my-default-model",
        system: context.systemPrompt,
        messages: context.messages,
        signal: options.signal,
      })) {
        if (event.type === "text") {
          options.onDelta?.({ kind: "text", text: event.text });
          continue;
        }
        items.push({
          type: "message",
          role: "assistant",
          content: [{ type: "output_text", text: event.text }],
        });
        stopReason = event.truncated === true ? "length" : "stop";
        const input = event.inputTokens ?? 0;
        const output = event.outputTokens ?? 0;
        usage = { input, output, total: input + output };
      }

      return { items, stopReason, usage };
    } catch (error) {
      return {
        items: [],
        stopReason: options.signal?.aborted === true ? "aborted" : "error",
        errorMessage: error instanceof Error ? error.message : String(error),
      };
    }
  };
}
```

To make tools work, translate `context.tools` into your client's tool format and translate the model's tool calls back into items of this shape:

```ts
const toolCall: ResponseItem = {
  type: "function_call",
  call_id: "call_abc123",
  name: "read",
  arguments: '{"path":"README.md"}',
};
```

`toolCallsOf` in the loop selects items where `type === "function_call"` and `call_id !== undefined`, then reads `name` (defaulting to `""`), and `arguments` (defaulting to `"{}"`). Results come back to you on the next turn as `{ type: "function_call_output", call_id, output }` items already in `context.messages`; see [Tools](./tools.mdx) for the execution side.

<Callout title="ResponseItem is deliberately open">
  `ResponseItem` in `@june/schema` declares a handful of known fields plus `[key: string]: unknown`.
  Provider-specific fields such as `encrypted_content` survive a round trip through the session, so
  you can return whatever your provider needs to replay its own state on the next turn.
</Callout>

## Not built yet

- **Retry and backoff.** `streamResponses` performs exactly one `fetch`. A 429 or 5xx becomes a thrown error, which `createProviderStreamFn` turns into `stopReason: "error"`, which ends the run. Nothing retries it, not the client, not the loop, not the harness.
- **Stream resumption.** A dropped connection loses the turn. There is no partial-response handle to reconnect to.
- **Non-Responses wire dialects.** `ResponsesApi` is `"responses" | "codex-responses"`. Adapting a chat-completions or Anthropic-shaped API means writing your own `StreamFn`, not adding a provider block.
- **Model discovery.** `Provider.models` is a hand-written list; nothing queries the provider for it.
- **Multi-account.** `CredentialStore` holds one credential per provider id.
