The agent loop drives model turns, tool batches, steering, and follow-up messages. It has no session,
storage, provider catalog, or credential dependency.

`agent-loop.ts` and `types.ts` define the implementation. The conformance suite lives in
`packages/core/test/upstream/agent-loop.test.ts`.

## Message contract

The loop carries `AgentMessage`. Without declaration merging, that is the neutral `Message` union:

```ts title="Message"
type Message = UserMessage | AssistantMessage | ToolResultMessage;
```

An assistant turn is one `AssistantMessage`. Its content can contain text, thinking, and tool-call blocks.
Executed tools produce separate `ToolResultMessage` values with strict text/image content. Provider adapters
encode those values at request time; the loop never stores or interprets a provider wire item.

## Entry points

Use `agentLoop` when you want an async event stream:

```ts title="agentLoop"
const events = agentLoop(prompts, context, config, signal, streamFn);

for await (const event of events) handleEvent(event);
const newMessages = await events.result();
```

Use `runAgentLoop` when another component owns event delivery:

```ts title="runAgentLoop"
const newMessages = await runAgentLoop(prompts, context, config, emit, signal, streamFn);
```

`agentLoopContinue` and `runAgentLoopContinue` resume from an existing context without appending a new prompt.
The context must be non-empty and must not end with an assistant message.

The return value is `AgentMessage[]`: new prompts plus every message created by this invocation. Continue
variants exclude messages already present in the supplied context.

## Required configuration

`AgentLoopConfig` requires two fields:

- `model`: the concrete `Model<Api>` used for the next request.
- `convertToLlm`: converts the extensible `AgentMessage[]` transcript to provider-neutral `Message[]`.

When an application has not declaration-merged custom agent messages, `convertToLlm` can filter to the three
standard roles and pass them through.

Optional configuration includes the `SimpleStreamOptions` request fields plus:

- `transformContext` for pruning or injecting context before conversion;
- `beforeToolCall` and `afterToolCall` hooks;
- `prepareNextTurn` and `shouldStopAfterTurn`;
- `getSteeringMessages` and `getFollowUpMessages`;
- `toolExecution`, either `parallel` (default) or `sequential`.

## Turn order

One turn follows this order:

1. Emit `turn_start` and inject queued messages.
2. Apply `transformContext`, then `convertToLlm`.
3. Call `StreamFn` and forward its assistant-message events as `message_update`.
4. Append the completed `AssistantMessage`.
5. Validate and execute its tool calls.
6. Append `ToolResultMessage` values in tool-call source order.
7. Emit `turn_end`.
8. Apply `prepareNextTurn`, `shouldStopAfterTurn`, steering, and follow-up policy.

A normal assistant response with no tool calls and no queued input ends the run. A tool batch causes another
model turn unless every finalized result requests termination.

## Tools

`AgentTool` extends the TypeBox-backed neutral `Tool` contract. `parameters` is a `TSchema`; the loop validates
and coerces provider arguments before calling `execute`. `prepareArguments` is an optional compatibility seam
for raw arguments that must be normalized before schema validation.

```ts title="echo-tool.ts"
import { Type } from "typebox";
import { toolResultContent } from "@uji-ai/core";

const echoParameters = Type.Object({ value: Type.String() });

const echo = {
  name: "echo",
  label: "Echo",
  description: "Return one string.",
  parameters: echoParameters,
  async execute(_toolCallId, { value }) {
    return { content: toolResultContent(value), details: undefined };
  },
};
```

Parallel batches validate and prepare calls in source order, execute allowed calls concurrently, emit
`tool_execution_end` in completion order, and append result messages in source order. A tool can force a batch
to run sequentially with `executionMode: "sequential"`.

If an assistant response stops for length while containing tool calls, the loop executes none of them. It emits
an error result for each call so the model can retry with complete arguments.

## Events

The loop emits:

- `agent_start` and `agent_end`;
- `turn_start` and `turn_end`;
- `message_start`, `message_update`, and `message_end`;
- `tool_execution_start`, `tool_execution_update`, and `tool_execution_end`.

`message_update.assistantMessageEvent` is the provider event (`text_*`, `thinking_*`, or
`toolcall_*`). Clients should render the event they understand and ignore unsupported content.

Every event sink call is awaited. A rejected sink or configuration callback interrupts the low-level loop; it
is not converted into a synthetic provider error.

## Stream ownership

Pass a `StreamFn` explicitly from the host to every low-level loop call. Core has no process-wide model
runtime or fallback registry.

See [Stream function](./stream-fn.mdx) for `Models.streamSimple` wiring and [Harness](./harness.mdx) for durable
execution.
