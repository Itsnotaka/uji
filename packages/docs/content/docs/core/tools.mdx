A tool is a plain object. `@uji-ai/core` does not have a tool registry, a decorator, or a builder: you construct an object that satisfies `AgentTool`, put it in an array, and hand the array to the agent loop or the harness. The seven built-in coding tools are factory functions that return exactly that shape.

## The AgentTool contract

`AgentTool<TParams, TDetails>` is declared in `packages/core/src/types.ts` and re-exported from `@uji-ai/core`.

`AgentToolResult<TDetails>` has required `content` (`(TextContent | ImageContent)[]`) and `details`
(your typed payload for logs and UI), plus optional `usage` and `terminate`. `toolResultContent(text)`
wraps the common all-text case. Sessions store these parts unchanged, provider adapters encode them at
request time, and clients ignore content they cannot render.

`TParameters` is a TypeBox schema. The loop validates provider arguments against it before execution.
`prepareArguments` is an optional normalization seam that runs before schema validation; `execute` receives
the resulting `Static<TParameters>` value.

### Rule 1: throw on failure

Do not put an error string in `content` and return normally. The loop wraps `execute` in a try/catch (`executePreparedToolCall`); a thrown error becomes `{ content: toolResultContent(message), details: {} }` with `isError: true`, and the tool result item written into the conversation is `Error: ${message}`. A normal return is recorded as a success no matter what the text says, so an error encoded in `content` reaches the model without the `Error:` prefix and is reported to `tool_execution_end` with `isError: false`.

### Rule 2: call onUpdate for progress

`onUpdate` is optional and may be absent. Each call emits a `tool_execution_update` event carrying a full `AgentToolResult<TDetails>`: a partial `content` plus whatever `details` you have so far. The loop stops accepting updates the moment `execute` settles and awaits the already-emitted update events before returning, so calling `onUpdate` after your promise resolves does nothing.

<Callout type="warn" title="Sequential is contagious">
  `executeToolCalls` runs the batch sequentially when `AgentLoopConfig.toolExecution ===
  "sequential"` **or** when any tool named in that batch declares `executionMode: "sequential"`. One
  sequential tool serializes every sibling call in the same turn. None of the seven built-ins set
  `executionMode`; `edit` and `write` use [`withFileMutationQueue`](#withfilemutationqueue) instead
  so they stay parallel.
</Callout>

## Writing a tool

The example below is a complete tool: a JSON Schema `parameters` object, hand-written argument validation, a typed `details` payload, one `onUpdate` call, and a throw on bad input.

```ts title="word-count-tool.ts"
import { toolResultContent, type AgentTool, type AgentToolResult } from "@uji-ai/core";

export interface WordCountDetails {
  words: number;
  lines: number;
}

const wordCountParameters: Record<string, unknown> = {
  type: "object",
  properties: {
    text: { type: "string", description: "Text to count words and lines in" },
  },
  required: ["text"],
};

interface WordCountInput {
  text: string;
}

export function createWordCountTool(): AgentTool<WordCountInput, WordCountDetails> {
  return {
    name: "word_count",
    label: "word count",
    description: "Count the words and lines in a string.",
    parameters: wordCountParameters,
    prepareArguments(params) {
      if (typeof params !== "object" || params === null) {
        throw new Error("Invalid arguments for word_count: expected an object");
      }
      const { text } = params as Record<string, unknown>;
      if (typeof text !== "string") {
        throw new Error('Invalid arguments for word_count: "text" must be a string');
      }
      return { text };
    },
    async execute(
      _toolCallId,
      { text },
      signal,
      onUpdate,
    ): Promise<AgentToolResult<WordCountDetails>> {
      onUpdate?.({ content: toolResultContent("counting"), details: { words: 0, lines: 0 } });
      if (signal?.aborted) throw new Error("Operation aborted");

      const words = text.split(/\s+/).filter((word) => word.length > 0).length;
      const lines = text.split("\n").length;
      return {
        content: toolResultContent(`${words} words, ${lines} lines`),
        details: { words, lines },
      };
    },
  };
}
```

### How details reaches the UI

`details` never goes to the model. Only `content` is included in the `ToolResultMessage`. `details` travels on the event stream:

| Event                   | When                                                | Carries                                                                                                             |
| ----------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `tool_execution_start`  | before `execute` is called                          | `toolCallId`, `toolName`, and `args`: the raw JSON `arguments` string off the assistant turn, not the parsed object |
| `tool_execution_update` | on every `onUpdate` call                            | `partialResult: AgentToolResult`, plus `toolCallId`, `toolName`, and the raw JSON `args` string                     |
| `tool_execution_end`    | after `execute` settles and `afterToolCall` has run | `result: AgentToolResult`, `isError`                                                                                |

Your UI subscribes to those events and narrows `result.details` by `toolName`. Note that the event types widen `details` to `unknown` (`AgentToolResult` without a type argument), so the narrowing is yours to write. On the failure path `details` is `{}`, not your payload.

`AgentLoopConfig.afterToolCall` can replace `details` before `tool_execution_end` fires, and does so with `after.details ?? result.details`.

## Tool sets

Four factories build tools. Membership differs between them; the tables are exhaustive.

| Factory               | Signature                                                                | Members, in order                                         |
| --------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| `createTool`          | `(toolName: ToolName, cwd: string, options?: ToolsOptions) => AgentTool` | one tool by name; throws `Unknown tool name: …` otherwise |
| `createCodingTools`   | `(cwd: string, options?: ToolsOptions) => AgentTool[]`                   | `read`, `bash`, `edit`, `write`                           |
| `createReadOnlyTools` | `(cwd: string, options?: ToolsOptions) => AgentTool[]`                   | `read`, `grep`, `find`, `ls`                              |
| `createAllTools`      | `(cwd: string, options?: ToolsOptions) => AgentTool[]`                   | `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`     |

`ToolName` is `"read" | "bash" | "edit" | "write" | "grep" | "find" | "ls"`, and `allToolNames` is a `Set<ToolName>` holding all seven. `ToolsOptions` is a bag with one optional key per tool (`read`, `bash`, `write`, `edit`, `grep`, `find`, `ls`), each holding that tool's own options type.

```ts title="build-tools.ts"
import { createAllTools, createTool, type ToolsOptions } from "@uji-ai/core";

const options: ToolsOptions = {
  bash: { commandPrefix: "set -euo pipefail" },
};

const tools = createAllTools(process.cwd(), options);
const bashOnly = createTool("bash", process.cwd(), options);
```

`cwd` is a plain string captured at construction time. It is the base for relative-path resolution in every tool and the working directory for `bash`. Nothing re-reads `process.cwd()` later, and no tool confines paths to `cwd`: an absolute path argument escapes it.

## Built-in tools

| Tool    | What it does                                                                                    | Arguments                                                                               | Options type      |
| ------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ----------------- |
| `read`  | Read a text file (1-indexed line window, head-truncated) or an image, attached as an image part | `path` (required), `offset?`, `limit?`                                                  | `ReadToolOptions` |
| `bash`  | Run a shell command in `cwd`, streamed and tail-truncated                                       | `command` (required), `timeout?` (seconds)                                              | `BashToolOptions` |
| `edit`  | Exact-text replacement of one or more disjoint blocks in one file                               | `path`, `edits: { oldText, newText }[]`                                                 | None              |
| `write` | Whole-file write, creating parent directories                                                   | `path`, `content`                                                                       | None              |
| `grep`  | Content search via `rg --json`                                                                  | `pattern` (required), `path?`, `glob?`, `ignoreCase?`, `literal?`, `context?`, `limit?` | `GrepToolOptions` |
| `find`  | Glob file search via `rg --files`                                                               | `pattern` (required), `path?`, `limit?`                                                 | `FindToolOptions` |
| `ls`    | Directory listing with `/` suffixes on directories                                              | `path?`, `limit?`                                                                       | `LsToolOptions`   |

Every tool's `label` equals its `name`.

### Defaults

| Tool    | Result cap                   | Output truncation                                                        | Notes                                |
| ------- | ---------------------------- | ------------------------------------------------------------------------ | ------------------------------------ |
| `read`  | none                         | `truncateHead` at 2000 lines / 51200 bytes                               | `offset` and `limit` have no default |
| `bash`  | none                         | `truncateTail` at 2000 lines / 51200 bytes                               | no default `timeout`                 |
| `edit`  | none                         | none                                                                     |                                      |
| `write` | none                         | none                                                                     |                                      |
| `grep`  | `limit` default 100 matches  | byte-only `truncateHead` at 51200 bytes; match lines capped at 500 chars | `context` default 0                  |
| `find`  | `limit` default 1000 results | byte-only `truncateHead` at 51200 bytes                                  |                                      |
| `ls`    | `limit` default 500 entries  | byte-only `truncateHead` at 51200 bytes                                  |                                      |

`grep`, `find`, and `ls` pass `maxLines: Number.MAX_SAFE_INTEGER` to `truncateHead` because their own row cap already bounds the line count, so only the byte limit applies.

### Options

| Options type      | Fields                                                                               |
| ----------------- | ------------------------------------------------------------------------------------ |
| `ReadToolOptions` | `imageProcessor?: ImageProcessor`, `autoResizeImages?` (default `true`)              |
| `LsToolOptions`   | `operations?: LsOperations` (`exists`, `stat`, `readdir`)                            |
| `GrepToolOptions` | `operations?: GrepOperations` (`isDirectory`, `readFile`)                            |
| `FindToolOptions` | `operations?: FindOperations` (`exists`, `glob`)                                     |
| `BashToolOptions` | `operations?: BashOperations` (`exec`), `commandPrefix?`, `shellPath?`, `spawnHook?` |

`edit` and `write` take no options: they use the local filesystem directly. Uji's direction is to grow one `ExecutionEnv` effects boundary instead of separate `operations` interfaces for each tool. `bash`'s `BashOperations` (the stand-in for `env.executeShell`) and the read-only `ls`/`grep`/`find` seams remain. `ImageProcessor` is the injectable image conversion/resizing hook (`(bytes, mimeType, { autoResizeImages }) => data/mimeType/hints or a failure message`); image processing needs native dependencies, which stay out of core.

Two of these do not do what the symmetry suggests. `GrepOperations` does not make ripgrep pluggable: `grep` always spawns `rg`, and the overrides only affect the directory check and the file reads used to render context lines. `FindOperations.glob` does: supplying `operations` replaces ripgrep entirely for `find`; omitting it selects the local `rg --files` path.

## bash

`createBashTool(cwd, options?)` returns `AgentTool<BashToolInput, BashToolDetails | undefined>`.

**Session.** There is none. Each call spawns a fresh shell, so `cd`, environment exports, and shell functions do not survive between calls. `getShellConfig` picks the shell in this order: `options.shellPath`, then Git Bash or `/bin/bash`, then `bash` on `PATH`, then `sh`.

**Command assembly.** When `commandPrefix` is set, the executed command is `` `${commandPrefix}\n${command}` ``. That string, plus `cwd` and a copy of `process.env`, is passed to `spawnHook` if you supplied one; whatever the hook returns is what gets spawned. The hook is the last point at which command, cwd, and env can be rewritten.

**Timeout.** The `timeout` argument is in seconds and has no default: a command with no `timeout` runs until it exits. Validation lives in `createLocalBashOperations`, not in the tool: a non-finite or non-positive value throws `Invalid timeout: must be a finite number of seconds`, and anything above 2147483.647 seconds throws. Custom `operations` receive the raw `timeout` value and are responsible for their own validation. On expiry, the local backend kills the whole process tree.

**Output accumulation.** stdout and stderr both feed one `OutputAccumulator`. It keeps a rolling decoded tail and, once the limits are exceeded, spills the full raw stream to a file in `os.tmpdir()` named `uji-bash-<8 hex bytes>.log`. That path is reported as `details.fullOutputPath` and in the trailing `[Showing lines …. Full output: …]` notice. Nothing deletes the file.

**Streaming.** `onUpdate` fires once immediately with `{ content: [], details: undefined }`, then at most every 100 ms while output arrives, then one final flush when output has arrived since the last update.

**Failure.** `bash` throws when the command exits non-zero, when it times out, and when the signal aborts. In all three cases the captured output is prepended to the thrown message, followed by `Command exited with code N`, `Command timed out after N seconds`, or `Command aborted`. A failing command is therefore an error tool result, not a successful result containing an error message.

**Process shutdown.** A running command is killed as a process group on timeout, explicit abort, or
harness close. A command that deliberately daemonizes and escapes that process group is no longer owned
by the tool; Uji does not keep a process-global registry for completed commands.

## edit

`createEditTool(cwd)` returns `AgentTool<EditToolInput, EditToolDetails>` and holds the file's mutation-queue lock for the whole read-modify-write.

**Matching.** Every `edits[].oldText` is matched against the _original_ file, not against the result of earlier edits in the same call. Before matching, the file's BOM is stripped and line endings are normalized to LF; both are restored on write, so a CRLF file stays CRLF.

Matching is exact-first: `fuzzyFindText` tries `indexOf` on the raw text, and only if that misses does it retry in a normalized space (NFKC, per-line trailing whitespace stripped, smart quotes, dashes, and exotic spaces folded). If any edit needed the fuzzy path, all edits are re-matched against the normalized text and the result is overlaid back onto the original bytes line-wise, so unchanged lines keep their original characters.

**Rejections.** `execute` throws on an empty `oldText`, on no match, on more than one occurrence of an `oldText`, on two edits whose matched ranges overlap, and when the edits produce content identical to the original.

**Input tolerance.** Two shapes are repaired before validation: `edits` arriving as a JSON string is `JSON.parse`d if it parses to an array, and legacy top-level `oldText`/`newText` are folded into `edits[]` as one more entry.

**Output.** `content` is `Successfully replaced N block(s) in <path>.` The structured payload is `EditToolDetails`:

| Field              | Type                  | Meaning                                            |
| ------------------ | --------------------- | -------------------------------------------------- |
| `diff`             | `string`              | display-oriented diff, 4 context lines             |
| `patch`            | `string`              | standard unified patch, 4 context lines            |
| `firstChangedLine` | `number \| undefined` | 1-indexed line of the first change in the new file |

<Callout title="Internal support modules">
  `tools/index.ts` re-exports the seven tool modules, `withFileMutationQueue`, image normalization
  types and the normalizer, and `support/truncate.ts`. `edit-diff.ts`, `image.ts`, `path-utils.ts`,
  `shell.ts`, and `output-accumulator.ts` remain internal. The `Edit` input type is re-exported, but
  matching and diff implementation helpers such as `fuzzyFindText` remain internal.
</Callout>

## read

`offset` is 1-indexed and `limit` is a line count. Both are applied before truncation: the slice `[offset, offset + limit)` is taken first, then `truncateHead` enforces 2000 lines / 51200 bytes on the slice. Every truncation path appends a notice telling the model what to do next.

| Situation                             | Trailing notice                                                                                                  |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| line limit hit                        | `[Showing lines A-B of N. Use offset=B+1 to continue.]`                                                          |
| byte limit hit                        | `[Showing lines A-B of N (50.0KB limit). Use offset=B+1 to continue.]`                                           |
| `limit` stopped early, file continues | `[K more lines in file. Use offset=… to continue.]`                                                              |
| first line alone exceeds 50 KB        | no file text is returned; `content` is only the notice, which names a `sed`/`head` command to run through `bash` |

`read` throws when `offset` is past the end of the file.

**Images.** The image test uses the file's leading bytes, not its extension. `detectSupportedImageMimeType` (`tools/support/image.ts`) reads the buffer and recognizes JPEG, non-animated PNG, GIF, WebP, and BMP. A renamed `.txt` is still detected; a `.png` that is not really a PNG is read as text. A recognized image returns two content parts: `{ type: "text", text: "Read image file [<mime>]" }` and `{ type: "image", data, mimeType }` with the base64 payload.

The tool ignores `offset` and `limit` for images. With an `imageProcessor` configured, the bytes run through it first (conversion/resizing, `autoResizeImages` default `true`); a processor failure returns its message as text with no image part. Without a processor, BMP stays text-only because providers reject BMP and conversion needs an image library outside core. The content asks the caller to configure an `imageProcessor`.

Tools other than `read` can also return image parts (screenshot tools, MCP bridges). `normalizeToolResultImages(content, processImage, options?)` (`tools/support/tool-result-images.ts`) is the once-at-history-entry pass that runs every image part through a processor so an oversized payload cannot make the provider reject each subsequent request. Standalone loop callers can compose it through `afterToolCall`. `AgentHarness` currently owns that callback and exposes no image-normalization option, so a host cannot yet apply this pass to arbitrary durable tool results without changing the harness.

Paths resolve through `resolveReadPathAsync`, which retries macOS NFD, curly-quote, and narrow-space AM/PM filename variants before giving up.

## grep, find, ls

`grep` and `find` shell out to `rg` on `PATH`. This is a Uji deviation: the upstream design ships managed `ripgrep` and `fd` binaries. When `rg` is missing, both tools throw `ripgrep (rg) not found on PATH`.

**grep.** Fixed flags are `--json --line-number --color=never --hidden`; `ignoreCase` adds `--ignore-case`, `literal` adds `--fixed-strings`, `glob` adds `--glob <value>`. Matches stream in and the child is killed as soon as `limit` is reached. With `context: 0` the match line comes straight from ripgrep's JSON; with `context > 0` the file is read and a `path:line: text` / `path-line- text` block is rendered around it. No match is a success, not an error: `content` is `No matches found`.

**find.** Backed by `rg --files --color=never --hidden`, filtered by `--glob`. `--no-require-git` is added only when no ancestor of the search path contains a `.git` directory, so inside a repo the ordinary git-aware ignore behaviour applies. A pattern containing `/` that is not already anchored is prefixed with `**/`, so `src/**/*.spec.ts` matches at any depth.

Results are relativized against the search root and normalized to `/` separators. No match returns `No files found matching pattern`.

**ls.** Uses `readdir` plus one `stat` per entry, sorted case-insensitively with `localeCompare`. Directories get a `/` suffix. Entries that cannot be `stat`ed are skipped silently, so the output can be shorter than the directory. An empty directory returns `(empty directory)`.

All three append a bracketed notice when a cap is hit, and mirror it in `details` as `matchLimitReached`, `resultLimitReached`, or `entryLimitReached` (the limit value that was applied) plus `truncation`.

## withFileMutationQueue

Tool calls in one batch run in parallel by default. Two calls that mutate the same file would then interleave their read-modify-write, and the second writer would silently discard the first one's change. `withFileMutationQueue` is the process-global per-file mutex that prevents this:

```ts title="withFileMutationQueue"
withFileMutationQueue<T>(filePath: string, fn: () => Promise<T>): Promise<T>
```

The queue key is the file's `realpath`, falling back to the resolved path when the file does not exist yet, so two aliases of the same file share a lock and different files still run concurrently. `edit` and `write` already wrap their whole body in it. Wrap your own tool the same way when it mutates a file:

```ts title="touch-tool.ts"
import { utimes } from "node:fs/promises";
import { resolve } from "node:path";
import type { AgentTool } from "@uji-ai/core";
import { toolResultContent, withFileMutationQueue } from "@uji-ai/core";

interface TouchInput {
  path: string;
}

export function createTouchTool(cwd: string): AgentTool<TouchInput, undefined> {
  return {
    name: "touch",
    label: "touch",
    description: "Update a file's access and modification times.",
    parameters: {
      type: "object",
      properties: { path: { type: "string", description: "File to touch" } },
      required: ["path"],
    },
    prepareArguments(params) {
      if (typeof params !== "object" || params === null) {
        throw new Error("Invalid arguments for touch: expected an object");
      }
      const { path } = params as Record<string, unknown>;
      if (typeof path !== "string") {
        throw new Error('Invalid arguments for touch: "path" must be a string');
      }
      return { path };
    },
    async execute(_toolCallId, { path }) {
      const absolutePath = resolve(cwd, path);
      return withFileMutationQueue(absolutePath, async () => {
        const now = new Date();
        await utimes(absolutePath, now, now);
        return { content: toolResultContent(`Touched ${path}`), details: undefined };
      });
    },
  };
}
```

Hold the lock across every `await`, and check `signal?.aborted` between them rather than rejecting from an abort listener. `edit` and `write` do it that way on purpose: rejecting from a listener would release the queue while a filesystem write is still in flight.

## Truncation helpers

`support/truncate.ts` is re-exported from the package root, so your own tools can use the same limits as the built-ins.

| Export                            | Purpose                                                                                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `truncateHead(content, options?)` | keeps the beginning; never returns a partial line. When line 1 alone exceeds the byte limit it returns empty `content` with `firstLineExceedsLimit: true` |
| `truncateTail(content, options?)` | keeps the end; the only helper that can return a partial line, flagged as `lastLinePartial`                                                               |
| `truncateLine(line, maxChars?)`   | caps one line, appending `... [truncated]`; `maxChars` defaults to `GREP_MAX_LINE_LENGTH`                                                                 |
| `formatSize(bytes)`               | `"512B"`, `"50.0KB"`, `"1.2MB"`                                                                                                                           |
| `DEFAULT_MAX_LINES`               | `2000`                                                                                                                                                    |
| `DEFAULT_MAX_BYTES`               | `51200` (50KB)                                                                                                                                            |
| `GREP_MAX_LINE_LENGTH`            | `500`                                                                                                                                                     |

`TruncationOptions` is `{ maxLines?, maxBytes? }`; whichever limit is hit first wins. `TruncationResult` reports `content`, `truncated`, `truncatedBy` (`"lines" | "bytes" | null`), `totalLines`, `totalBytes`, `outputLines`, `outputBytes`, `lastLinePartial`, `firstLineExceedsLimit`, and the `maxLines`/`maxBytes` that were applied.

<Callout type="warn" title="Attach a replay policy before using tools with the harness">
`HarnessTool` is `AgentTool & { replay?: "never" | "safe" }`, and that field decides what a crash resume does with a tool call that started but never settled. The default is `"never"`. Mark a tool `"safe"` only when re-running it with the same arguments is indistinguishable from running it once: `read`, `grep`, `find`, and `ls` qualify; `bash`, `edit`, and `write` do not. [The harness page](./harness.mdx#harnesstool-and-the-replay-policy) documents both paths and what a replayed call does not get.
</Callout>
